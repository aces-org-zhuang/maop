# Design Governance Checklist

用于技术设计事前推演门禁和定版评审。任一关键项未通过时，设计不得进入实现计划、高风险 POC 或 `implementation-delivery`。

- [ ] 已在方案前使用 `reasoning-map` 推演技术栈、模块边界、依赖、状态、契约、运行时和验证链路。
- [ ] 技术栈归一：系统尽可能使用既有开发语言、框架、运行时和构建工具；新增语言/运行时必须说明不可替代原因、维护成本和验证方式。
- [ ] 特性模块唯一归属：同一特性、能力块或业务规则只能有一个主模块/主服务/主组件负责；不得在多个模块重复实现同一能力。
- [ ] 依赖唯一性：同一特性或能力块只能有一个 primary 依赖；同质依赖必须标为 fallback、alternative 或 rejected。
- [ ] 契约归属清晰：共享 API、IPC、schema、事件、CLI 或配置契约有唯一 owner，并列出消费者。
- [ ] 数据与状态单一来源：同一业务状态、缓存、持久化记录或派生数据有明确 source of truth，不创建并行状态源。
- [ ] 层级边界清晰：UI、应用服务、领域逻辑、基础设施、外部服务和工具适配层没有反向依赖或跨层偷连。
- [ ] 运行时边界可维护：新增进程、线程、队列、服务、daemon、browser、sandbox 或外部 CLI 必须说明生命周期、就绪信号、失败处理和关闭路径。
- [ ] 构建复杂度受控：新增包管理器、构建链、native dependency、codegen、submodule 或二进制资源必须说明锁定方式和 build/test/package 验证。
- [ ] 可回滚和可迁移：高风险设计包含 feature flag、兼容层、迁移策略、回滚路径或最小 POC Gate。
- [ ] 不重复造轮子：已有模块、平台抽象、工具链或依赖可满足需求时，优先复用；自研必须说明现有方案不适用的证据。
- [ ] 设计输出包含 RED 点：未满足的治理项必须保留为 RED 风险和补证动作，不得在最终结论中隐去。
