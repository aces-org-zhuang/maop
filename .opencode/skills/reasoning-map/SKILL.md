# 推演全景

使用本技能执行结构化、递归式的图谱推演。推演过程必须通过每轮 ASCII 图渐进展示，而不是通过表格、长段落或最后一次性总结展示。目标不是产出长报告、表格堆叠或线性推理记录，而是用带注释的 `Round N Map` 和 `Final Panorama Map` 展示判断演进、关键红绿节点、根因/缺口和下一步动作。

## 不可妥协检查清单

写最终答案前，先在草稿中自检以下事项：

- 已明确选择 `problem-location`、`feature-panorama` 或二者同时使用。
- 第一个实质性分析产物是图形化 ASCII 地图，而不是表格或线性段落。
- 默认输出聚焦“推演图”，每一轮推演都要展示当前地图，不要展示评分规约、宽泛解释或大段表格。
- 每个重要节点只使用一个标记：`🟢` 或 `🔴`。
- 每个 `🔴` 节点都有 `{}` 内联原因，或有边界清晰的验证动作。
- 当存在症状、消费者、生成物、事件或异步交接时，已识别直接关联和根本关联。
- 涉及生成文件、数据、事件或持久状态时，已建模“生产者 -> 生成物/状态 -> 提交/就绪 -> 消费者”。
- 当异步、调度、生命周期、队列、重试、缓存或就绪信号会影响正确性时，已包含“时序透镜”。
- 不输出 `Mutation Log`、推演过程表、退出检查表或评分表。
- 没有宽泛的 `🔴` 节点停留在未下钻、未横向扩散、也无明确下一步验证的状态。
- 输出语言遵循用户语言，除非用户另有要求。

## 何时不要使用

简单任务不需要递归图谱推演时，不要使用本技能：

- 简单事实问答、命令查询或简短解释。
- 目标明确、无模糊根因或特性全景需求的直接代码编辑。
- 用户要求对现有差异做普通代码评审时；此时优先使用代码评审技能。
- 无需图形化故障/能力推演的需求编写、PRD 生成、UI 设计或实现计划。
- 用户明确要求简洁回答，且不要结构化地图的对话。

如果请求接近诊断、设计或评审，但用户要求 `推演`、绘制全景、分析 RED/GREEN 点、追踪根因/直接关联，或分析时序/依赖，则使用本技能。

## 默认不提问，证据保真度优先

除非提示完全没有可识别主题，否则不要在开始推演前向用户提澄清问题。不要把可通过既有资源获得或构造验证的信息直接遗留为 `🔴` 未知节点；应先为当前问题选择最高保真的可获得证据。只有目标环境不可访问、验证成本明显超出当前任务、存在破坏性或安全风险、需要用户私有上下文，或已探索但仍无法证明时，才把缺失信息作为 `🔴` 未闭环节点放入地图。

证据保真度选择规则：

1. 先判断目标事实必须在哪个环境或链路中成立：生产/部署环境、等价本地环境、模拟环境、测试环境、单模块执行环境、静态契约或纯设计约束。
2. 在不越过用户边界的前提下，优先使用最接近目标事实的证据：真实流程观察、等价环境验证、DT/自动化测试、片段化执行、CLI 化探针、日志/产物读取、配置/schema/契约检查、源码静态追踪、文档规则。
3. 如果完整运行不可行，应主动构造较高保真的替代验证，例如最小复现、模块级执行、协议/数据片段执行、测试替身、录制日志回放或针对关键转换的探针，而不是直接退回纯逻辑推演。
4. 只在高保真证据不可访问、不可安全执行、成本不合理或用户禁止时，才使用静态分析和逻辑推演作为降级证据，并在图中标出证据层级和缺口。
5. 若用户明确要求“先推演，确认后再行动”，仍可执行不会修改目标系统状态的证据收集和验证；禁止的是修复、写入业务文件、破坏性运行或未经确认的高风险动作。
6. 若证据收集本身也被用户禁止，才把证据缺口标为 `🔴`，并说明为了把该节点转为 GREEN 需要哪一类证据。

用逻辑预检替代用户提问：

```text
预检假设
- 范围：根据用户措辞推断；不确定时把边界节点标为 🔴。
- 模式：推断 `problem-location`、`feature-panorama` 或二者。
- 最大深度：默认 <=Level7，除非用户指定其他深度。
- 证据：先选择可获得的最高保真证据层级；完整环境不可运行时，优先构造等价、DT、片段化、CLI 化或日志/产物回放证据；仍不可得才标为 🔴 证据缺口。
- 系统边界：绘制可能的上游、核心路径、下游、副作用和可观测性分支。
```

这样做是因为推演不能停滞，也不能用“未知”或纯逻辑猜测替代可获得证据。未知信息是全景的一部分，但可通过较高保真证据闭环的未知，必须先验证或构造替代验证后再遗留。

## 输出规模控制

默认使用渐进图模式（`progressive-map`）。输出包含一句话结论、每轮当前推演图、最终合成图、图下注释和下一步动作。对中文用户输出时，优先写中文字段名；英文 token 仅作为括号或固定标识保留。

即使用户要求“完整报告”“全量推演”“逐层下钻”或“Level0 到 LevelN”，也不要输出详细推演表格。需要更完整时，按轮次展示 `Round N Map`，每轮都必须是一张 ASCII 图，并用短 bullet 补充必要说明。

`progressive-map` 模式不得省略图形化地图、RED/GREEN 标记，以及相关时的根因/直接关联检查或时序透镜。必要说明写在图内或图下 3-5 条短句中。

不要仅因为用户使用了“推演”“RED/GREEN”“根因”“时序”等词就输出长报告；这些词只说明应使用本技能。展示过程时只展示每轮推演图，不展示表格式过程明细。

## 模式选择

先把任务归入一个模式：

- `problem-location`：用户报告 bug、失败、异常行为、故障、回归、性能问题、集成问题或未知根因。参考 `references/mode-problem-location.md`。
- `feature-panorama`：用户希望设计、评估或补齐新特性、缺失能力、产品流程、架构新增或实现方案。参考 `references/mode-feature-panorama.md`。

如果任务同时包含故障和目标状态，先运行 `problem-location`，再对修正后或新增目标能力运行 `feature-panorama`。

## 核心循环

所有模式都应用此循环：

1. 预检：推断模式、范围、最大深度、可能系统边界、证据基础和未知项。不要提问；把未知项分为“可用高保真证据验证”“可用替代证据验证”“只能静态/逻辑推演”“不可探索”。
2. 对可验证未知执行证据保真度选择：优先接近真实目标链路；完整环境不可用时，构造等价环境、DT/测试、片段执行、CLI 化探针、日志/产物回放、契约/schema 检查等替代证据；探索结果要回写到地图标记和注释中。
3. 把 `Level0` 画成图，而不是单链路。包含上游输入、主路径、下游消费者、副作用、共享状态、可观测性和相关时序分支。
4. 给图中每个节点标记 `🔴 RED` 或 `🟢 GREEN`。
5. 检查分解是否 MECE：没有重要分支缺失，兄弟节点职责不重叠。
6. 用证据、假设或明确不可探索未知项解释每个标记。
7. 选择下一批前沿点：宽泛、根因相关、时序相关或阻塞闭环的所有 `🔴` 节点。
8. 对每个前沿点选择操作：继续探索、下钻、横向扩散、增加时序透镜、拆分/合并节点或改变标记。
9. 同时追踪直接关联和根本关联。不要停在症状出现组件；如果上游生产者、生成器、调度器或契约负责人可能是根因，要继续追溯。
10. 检查顺序和时序。节点逻辑上正确，但如果执行太早、太晚、无协调并发、数据未持久化、状态已陈旧或跨异步边界缺少就绪保证，也仍然是 `RED`。
11. 在循环中变更地图：增加缺失节点、删除无效节点、拆分重叠节点、合并重复节点、更新标记，并在准确位置附短注释。每轮变更后都输出当前 `Round N Map`，避免只在最后展示导致前序推演丢失。
12. 执行内部闭环判断。如果任一停止条件失败，继续下一轮；若较高保真证据经选择和尝试后仍不可得，把未闭环区域标为带证据类型和验证动作的有界 `🔴` 后续项。
13. 交付最终带注释的全景图；最终图必须能回看每轮地图中的关键变更。
14. 用 3-5 条短 bullet 总结直接症状、根本关联、下一步和剩余未知项。

这个循环重要，因为复杂问题和特性缺口通常隐藏在分支、转换、依赖、副作用、时序和缺失证据中，而不是单个显眼组件里。

## 图优先要求

除非实际系统被证明是单链路，否则避免单链推演。多数任务需要包含多种分支类型的图：

```text
图骨架
                       ┌─ [可观测性分支]
                       ├─ [权限/配置分支]
[上游输入] -> [核心转换] -> [下游消费者]
                       ├─ [共享状态/生成物分支]
                       ├─ [时序/调度分支]
                       └─ [测试/证明分支]
```

全景图至少应考虑这些分支：

- 上游原因分支。
- 核心执行分支。
- 下游症状/消费者分支。
- 共享生成物/状态分支。
- 时序/调度分支。
- 可观测性/证据分支。
- 验证/测试/替代证明分支。
- 相关时的横切约束分支：权限、安全、兼容性、国际化、性能、可靠性。

如果某个分支无关，也要作为 `🟢` 边界纳入并说明理由。若证据不足以声明无关，则标为 `🔴 {缺失证据}`。

## 推演原则

在整份报告中使用这些原则：

- MECE：每一层都应在所选范围内互斥且穷尽。若兄弟节点重叠，按职责、生命周期阶段或数据所有权拆分。若缺少分支，添加并标 RED 直到评估完成。
- 证据保真度最大化：推演结论应尽量由当前可获得的最高保真证据支撑。完整目标环境不可运行时，应主动寻找等价验证、DT/自动化测试、片段执行、CLI 化探针、日志/产物回放或契约检查，而不是直接用逻辑推演替代。
- 直接关联 vs 根本关联：区分症状出现位置与原因产生位置。例如特性 2 读取文件 A 后报格式错误时，要追踪特性 1 是否生成了错误文件 A，而不是直接归咎于特性 2。
- 异步边界追踪：显式建模“生产者 -> 持久化/提交 -> 通知/就绪 -> 消费者”链。缺少等待、竞态、最终一致性、延迟写入、队列乱序、重试和陈旧缓存，在被证明安全前均为 RED。
- 时序与调度：记录节点执行顺序。一个特性或故障点可在孤立状态为 GREEN，但在实际调度中若执行时机错误或生命周期状态不对，则为 RED。

## 可视化地图要求

主要输出是 ASCII 全景图，而不是表格。禁止用 Markdown 表格承载关键结论、推演过程、行动项或未闭环节点；如确需补充，只能在图后使用 3-5 条短 bullet。

不确定如何画图或注释时，阅读 `references/map-examples.md`。它包含何时下钻、何时横向扩散、标记放置位置和注释写法的具体例子。

只能使用这些标记：

- `🟢`：GREEN 节点。已验证健康、已有、充分或有意边界化。
- `🔴`：RED 节点。故障、缺失能力、不确定性、时序风险、根因候选或未闭环依赖。

如果用户终端、渲染器、日志系统或请求格式不能可靠显示 emoji，整份报告使用 ASCII 备用标记：

- `[GREEN]`：与 `🟢` 含义相同。
- `[RED]`：与 `🔴` 含义相同。

同一份报告不要混用 emoji 标记和备用标记。默认优先使用 emoji；当用户报告 Unicode/emoji 显示问题、要求 ASCII 兼容输出，或输出面向日志/CI/纯文本终端时，切换到备用标记。

ASCII map 规则：

- 把标记放在节点内部或紧邻节点前：`[🔴 L1.2 文件 A 生成器]`。
- 使用 ASCII 备用标记时，把备用标记放在相同位置：`[[RED] L1.2 文件 A 生成器]`。
- 在受影响位置添加短内联注释：`{根因?}`、`{直接症状}`、`{提交前读取}`、`{契约负责人}`、`{缺少就绪信号}`。
- 用缩进、分支或嵌套框展示纵向下钻。
- 从被扩散的准确节点展示横向分支。
- 用箭头展示生产者/消费者与时序：`生成 -> 提交 -> 就绪 -> 消费`。
- 循环改变地图是内部行为，不要输出地图变更日志。
- 最终报告必须包含 `Final Panorama Map`，并把所有重要 RED/GREEN 标记和注释放在对应位置。
- 默认结果图要尽量让用户“看图即懂”：根因、直接症状、目标结构和行动落点都应写进图中，而不是移到表格里。
- 默认输出多轮阶段图和最终合成图；每轮图都应体现上一轮保留节点、新增节点和状态变化。

推荐 ASCII 模式：

```text
Level0 全景
[🟢 触发]
   -> [🔴 特性 1 生产者 {根因?}]
        -> [🔴 文件 A {格式契约?}]
             -> [🔴 就绪信号 {缺失}]
                  -> [🔴 特性 2 消费者 {直接症状}]

从 [🔴 文件 A] 横向扩散
   ├─ [🔴 Schema 版本 {负责人不清}]
   ├─ [🟢 存储路径 {已验证}]
   └─ [🔴 写入完成 {消费者可能提前读取}]
```

```text
时序透镜
t0 [🟢 触发]
t1 [🔴 特性 1 写入文件 A {尚未持久化}]
t2 [🔴 特性 2 读取文件 A {提交前读取}]
t3 [🟢 文件 A 提交完成]
```

## RED/GREEN 语义

只使用这两种状态：

- `GREEN` 在 `problem-location` 中表示已验证健康、当前层级不相关或足够；在 `feature-panorama` 中表示已存在、足够、兼容或已设计。
- `RED` 在 `problem-location` 中表示故障点、风险点、证据缺失、证据保真度不足、行为不一致、未验证关键假设或未解决依赖；在 `feature-panorama` 中表示缺失能力、设计缺口、未解决依赖、不兼容假设、未实现路径或关键未知项。

不要引入 `YELLOW`、`ORANGE`、严重程度颜色、其他图标或替代状态名。如果证据不确定，把该点标为 `RED` 并说明原因是证据不足。

启用 ASCII 备用标记时，允许状态仍只有 `GREEN` 和 `RED`，写作 `[GREEN]` 和 `[RED]`。

## 内部停止条件

同时使用闭环控制和深度控制：

1. 当每个 `RED` 节点都有以下结果之一时停止：已识别根因或缺口、已边界化影响面、具体验证步骤、下一步动作或明确未解决问题。
2. 仅当用户给出严格最大深度时，才更早停止。
3. 默认最大深度为 `Level3`，除非任务明显需要更深分析。
4. 如果更深分析有价值但证据缺失，先选择并尝试当前可获得的最高保真证据；只有真实或替代证据仍不可得时，才停止并把缺失证据列为 `RED` 后续项，而不是编造事实。

停止前在内部运行闭环检查。不要把以下检查清单输出给用户：

```text
内部闭环检查
[ ] `Final Panorama Map` 存在，且是图形结构，不只是单链路。
[ ] 每个重要节点都有 🟢 或 🔴。
[ ] 每个 🔴 都有内联注释说明为什么是红点。
[ ] 直接关联和根本关联已标记，或已明确说明二者相同。
[ ] 涉及生成文件/数据/事件时，已建模“生产者 -> 生成物/状态 -> 提交/就绪 -> 消费者”。
[ ] 当异步、调度、生命周期或竞态风险存在时，已包含时序透镜。
[ ] 横向分支覆盖证据、测试、替代证明、共享状态和横切约束，或将其标为 GREEN 边界。
[ ] 没有宽泛 RED 节点停留在未下钻、也无有界验证动作的状态。
[ ] 输出中没有 Markdown 表格、Mutation Log、推演过程表、退出检查表或评分表。
```

如果任一项失败，继续循环。如果继续需要证据，先判断可获得的最高保真证据是什么；可安全收集或构造验证则执行，不可探索才添加有界 `🔴` 节点并标注“需要哪类证据验证”。这些检查只用于内部控制，不作为交付内容。

## 自验证规约

写最终答案前，在内部确认：

- 已选择 `problem-location`、`feature-panorama` 或二者同时使用。
- `Final Panorama Map` 位于支撑说明之前。
- 地图是带侧向分支的图形结构，不是单链路。
- 只使用 `🟢` 和 `🔴` 标记。
- 每个重要 `🔴` 都有内联原因或验证动作。
- 有一句话结论和下一步动作。
- 相关时已识别直接关联 vs 根本关联。
- 相关时已包含时序透镜。
- 未闭环 RED 已写进图内或图后短 bullet。
- 输出中没有 Markdown 表格、Mutation Log、推演过程表、退出检查表或评分表。

常见无效输出：

- 只有单线性链路，没有侧向分支。
- 使用 `YELLOW`、`ORANGE`、严重程度颜色或未批准状态标签。
- 用表格替代全景图。
- 默认输出大量表格，导致用户看不到核心地图结论。
- 展示 Mutation Log、退出检查或评分规约，而不是用每轮推演图展示判断演进。
- 停在直接症状处，没有检查上游根本关联。
- 生成物、异步事件、队列、重试、缓存或就绪交接场景缺少时序透镜。
- 存在 `backend`、`logic`、`system` 等宽泛 RED 节点，却没有下钻或验证动作。

## 执行指导

- 除非完全没有可识别主题，否则不要在第一张地图前提澄清问题。推断合理范围，并把不确定边界拆成可探索与不可探索。
- 只要有可识别主题，就立即开始推演，并优先选择当前可获得的最高保真证据。在报告中声明假设，并把证据不足的假设映射为 `🔴`。
- 不要在画第一张地图前要求日志、文件、图表或确认。可访问或可构造验证的生成物、代码、配置、契约、运行片段、测试、日志或产物要先用于闭环；证据不可得才成为 `🔴 证据缺口` 节点。
- 优先使用具体节点名，避免含糊标签。例如用 `渲染进程请求`、`协议适配权限检查`、`凭据解密`、`验证器产物`，而不是 `backend` 或 `logic`。
- 每一层保持聚焦。一个层级应分解一个 `RED` 节点，而不是重新开始全局分析。
- 横向扩散应在相关时覆盖上游依赖、下游消费者、共享状态、配置、可观测性、测试、部署和用户工作流。
- 每个 RED 症状都需要直接关联和根本关联检查。如果二者相同，说明原因；如果不同，优先处理根本关联。
- 每个生产者/消费者关系都需要时序检查。包含创建时间、持久化/提交点、就绪信号、消费者读取时间、重试/回退行为。
- 不要用表格替代或解释全景图。需要解释时，用图内注释或图后 3-5 条短 bullet。
- 不要在发现第一个可能根因后停止。继续边界化兄弟分支为 `🟢` 或带行动的 `🔴`。
- 不要隐藏不确定性。不确定性是 `RED` 节点，因为它阻塞闭环。
- 遵循用户语言。用户用中文时，输出中文标题和解释；用户用英文时输出英文，除非另有要求。
- 如果另一个专门技能更适合作为主工具，仅当明确需要图谱推演时使用本技能；否则让专门技能处理任务。
