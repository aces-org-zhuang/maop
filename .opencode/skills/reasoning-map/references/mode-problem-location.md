# Mode: problem-location

当任务需要定位故障、回归、未知根因、断裂流程、验证失败、性能异常、集成失败或行为不一致时，使用此模式。

## 目标

产出故障全景，展示：

- 故障可能从哪里进入系统。
- 故障可能如何传播。
- 哪些点已验证健康。
- 哪些点仍然故障、可疑或未验证。
- 每个 RED 点需要什么证据才能闭环。
- 最终故障链路必须是带红/绿标记和内联注释的 ASCII map，并把注释放在失败或可疑位置。

即使证据不完整，也要开始，但不要把可获得或可构造的证据直接遗留。缺失的复现步骤、日志、代码、schema、时序或环境事实，应先选择当前可用的最高保真证据：真实流程观察、等价环境验证、DT/自动化测试、片段化执行、CLI 化探针、日志/产物读取、配置/schema/契约检查或源码静态追踪。只有这些证据不可得、需要用户私有上下文、风险过高或超出当前权限时，才作为图中的 `🔴` 证据节点，而不是开始前的阻塞项。

## 证据保真度规则

在绘制或更新故障图前，先对可验证未知选择最高保真的可获得证据：

1. 先判断故障必须在哪个目标链路中成立，以及当前能接近该链路到什么程度。
2. 完整目标环境可用时，优先观察真实流程或真实失败转换。
3. 完整目标环境不可用时，主动构造等价验证：DT/自动化测试、模块级执行、协议或数据片段执行、CLI 化探针、日志/产物回放、schema/契约校验。
4. 只有运行或替代验证不可得时，才退到源码静态追踪、文档和规则检查；逻辑推演必须标出证据保真度不足。
5. 把证据结果回写到地图；只有证据选择并尝试后仍缺失的节点才能保留为 `🔴` 未闭环节点。
6. 如果用户要求“确认后再行动”，仍允许不会改变目标系统状态的证据收集和替代验证；禁止的是修复、写业务文件、破坏性运行或未经确认的高风险动作。

## Level0 链路模式

把 Level0 构造成最宽的用户可见或系统可见图。除非每个侧向分支都已明确边界化，否则不要把 Level0 限制为单链路。常见模式：

| 领域 | Level0 链路示例 |
| --- | --- |
| UI 问题 | 用户动作 -> 渲染状态 -> IPC/预加载桥 -> 主进程处理器 -> 服务 -> 持久化/外部进程 -> UI 反馈 |
| 后端问题 | 请求 -> 校验 -> 鉴权/权限 -> 业务逻辑 -> 数据访问 -> 副作用 -> 响应 |
| CLI/工具问题 | 命令输入 -> 配置加载 -> 环境检测 -> 执行 -> 输出解析 -> 退出状态 |
| 集成问题 | 调用方 -> 协议适配 -> 凭据/权限 -> 远端或本地服务 -> 响应映射 -> 消费方 |
| 性能问题 | 触发 -> 工作队列 -> 热点路径 -> 资源争用 -> 超时/背压 -> 用户可见卡顿 |

如果实际系统不同，可以调整图，但要保留从左到右的因果流，并附上证据、时序、共享状态和验证侧向分支。

problem-location 的 Level0 通常应包含：

```text
故障图分支
                                      ┌─ [可观测性/证据]
                                      ├─ [配置/权限/环境]
[上游触发/输入] -> [核心故障路径] -> [下游症状/消费者]
                                      ├─ [共享生成物/状态/缓存]
                                      ├─ [时序/调度/重试]
                                       └─ [测试/复现/替代证明]
```

先画 Level0 ASCII map。示例：

```text
Level0 故障全景
[🟢 用户动作]
   -> [🟢 渲染事件]
      -> [🔴 IPC/预加载桥 {直接症状?}]
         -> [🔴 主进程处理器 {根因? 缺少校验}]
            -> [🟢 服务调用]
               -> [🔴 用户反馈 {错误被隐藏}]
```

如需更完整的地图示例，包括何时下钻和何时横向扩散，读取 `references/map-examples.md`。

## 标记规则

仅当有足够证据表明节点在当前推演层级不相关或健康时，才标记 `GREEN`。

满足以下任一条件时标记 `RED`：

- 节点直接失败。
- 节点证据缺失或矛盾。
- 节点依赖未验证假设。
- 节点是合理传播点。
- 节点可能通过重试、回退、缓存、陈旧状态、吞掉错误或不清晰的可观测性隐藏故障。
- 节点近期有变更且与症状相关。

## 纵向下钻

对每个 RED 节点，按内部机制拆解：

1. 输入与前置条件。
2. 状态或配置读取。
3. 决策分支。
4. 外部调用或依赖。
5. 错误处理与回退行为。
6. 输出、副作用和可观测性。
7. 生产者/消费者契约与所有权。
8. 异步边界、就绪信号和调度顺序。

然后给每个子节点标记 RED/GREEN。

## 直接关联 vs 根本关联

不要把报错节点自动当作根因。分开回答两个问题：

| 问题 | 含义 |
| --- | --- |
| 直接关联 | 症状在哪里被观察到或抛出？ |
| 根本关联 | 哪个上游节点创建了无效状态、无效生成物、错误时序或缺失契约，使症状不可避免？ |

对生成物、数据、事件和异步失败使用此追踪模式：

```text
[🔴 生产者特性 {根因?}]
   -> [🔴 生成物/数据生成 {格式?}]
      -> [🔴 校验/序列化 {契约?}]
         -> [🔴 持久化/提交 {是否持久?}]
            -> [🔴 就绪信号 {缺失?}]
               -> [🔴 消费者特性 {直接症状}]
                  -> [🔴 解析/使用 -> 症状]
```

示例：如果 `特性 2` 因 `文件 A` 格式错误而失败，把 `特性 2 解析器` 标为直接关联 RED，然后追踪 `特性 1 文件 A 生成器`、schema 版本、写入完成和就绪信号。如果特性 1 生成了无效文件 A，则特性 1 是根本关联 RED。

## 时序检查

对每条可疑故障路径，写出实际顺序：

1. 触发时间。
2. 生产者执行时间。
3. 生成物/数据持久化时间。
4. 就绪通知时间。
5. 消费者读取/使用时间。
6. 重试、防抖、队列、取消或清理时间。

如果竞态、陈旧数据、缺少等待、队列乱序、提交前发出事件、消费者在生成完成前读取、清理早于消费，或回退掩盖实际失败转换，能解释故障，则把路径标为 `RED`。

用 ASCII 时间线表达时序：

```text
故障时序透镜
t0 [🟢 触发]
t1 [🔴 生产者开始]
t2 [🔴 消费者读取生成物 {提交前读取}]
t3 [🟢 生产者提交完成]
t4 [🔴 错误出现在消费者 {直接症状，不是根因}]
```

## 横向扩散

标记一个层级后，从每个 RED 节点横向扩散：

| 扩散区域 | 问题 |
| --- | --- |
| 上游 | 无效输入、陈旧状态、权限或缺失配置是否能造成该 RED 节点？ |
| 下游 | 谁消费这个输出？故障如何在那里表现？ |
| 共享状态 | 是否涉及缓存、存储、临时文件、socket、工作树、会话或凭据？ |
| 异步边界 | 是否有生产者生成后续消费者使用的数据或文件？就绪信号是否显式且可靠？ |
| 时序 | 调度、生命周期顺序、队列顺序、重试或清理时机是否可能造成故障，即使每个组件单独正确？ |
| 可观测性 | 日志、验证报告、遥测和用户反馈是否足够？缺失可观测性是 RED。 |
| 证据保真度 | 是否已使用当前可获得的最高保真证据？完整环境不可用时，是否构造了等价验证、DT、片段执行、CLI 化探针或日志/产物回放？ |
| 回归面 | 最近变更、依赖升级、环境变化或特性开关是否触达该路径？ |
| 测试面 | 哪些测试或替代证明应该发现该问题？缺少此故障路径覆盖是 RED。 |

## 故障全景结论

结尾包含这些类别：

- `Confirmed RED`：有证据支撑的故障点。
- `Probable RED`：高可能性点，只需一步验证。
- `Blocked RED`：缺少日志、复现数据、访问权限或用户确认时无法闭环的点。
- `GREEN Boundary`：已验证边界，用于防止范围蔓延。
- `Root RED`：创建无效状态、生成物、时序或契约破坏的上游来源。
- `Direct RED`：消费或暴露上游缺陷的症状位置。

同时包含最终 `Fault Panorama Map`，并把 `Root RED`、`Direct RED` 和 `GREEN Boundary` 注释放在 ASCII 图内的对应节点上。

## 推荐动作

优先选择最快降低不确定性的动作：

1. 先选择当前可获得的最高保真证据，避免把可证明信息遗留为未知。
2. 优先复现真实症状或隔离失败转换；真实环境不可得时构造等价、DT、片段化或回放验证。
3. 在最近的 RED 边界添加/检查目标证据。
4. 验证上游假设。
5. 验证下游传播。
6. 最后再提出修复或实现改动。

不要在产出第一张全景图前向用户索要缺失证据。先选择并尝试当前可获得的最高保真证据；真实或替代证据仍不可得的，放入最终 `Unclosed RED` 区域，并附需要的证据类型和验证动作。
