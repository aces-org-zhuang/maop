# 推演地图示例

构造 ASCII 全景图时使用本参考。示例展示何时下钻、何时横向扩散、红/绿标记放在何处，以及应附加什么注释。

## 0. 图优先循环形态

除非范围确实是线性的，否则不要只画单链路。从图形骨架开始，并在推演中不断变更它。

```text
推演循环
预检假设
   -> 绘制图形化 Level0
      -> 标记所有节点
         -> 选择 RED 前沿点
            -> 下钻 OR 横向扩散 OR 增加时序透镜 OR 变更节点
               -> 重新标记地图
                  -> 选择/补充当前最高保真证据
                     -> 运行退出检查
                        -> 若任一条件失败则继续
                        -> 若全部通过或剩余 RED 已边界化，则输出 Final Panorama Map
```

默认图骨架：

```text
Level0 图骨架
                                      ┌─ [🔴 可观测性/证据 {待检查}]
                                      ├─ [🔴 权限/配置 {待检查}]
[🔴 上游输入 {基于假设}] -> [🔴 核心转换 {推演中}] -> [🔴 下游消费者 {症状/目标}]
                                      ├─ [🔴 共享生成物/状态 {待检查}]
                                      ├─ [🔴 时序/调度 {待检查}]
                                      └─ [🔴 测试/替代证明 {尚未识别}]
```

如果某个分支被证明无关，把它改为 `🟢` 并标注边界：

```text
                                      ├─ [🟢 权限/配置 {GREEN boundary: 无鉴权/配置路径参与}]
```

## 0.1 默认不提问示例

如果用户只说“特性 2 读取文件 A 后报告格式错误”，不要先问更多细节。先声明假设，并把未知项作为 RED 节点映射出来。

```text
预检假设
- Mode: problem-location。
- 范围：文件 A 的生产者-消费者路径。
- 最大深度：默认 Level3。
- 证据：只有用户症状；日志/schema/源码文件都是缺失证据。
- 未知项作为 RED 节点进入地图，而不是变成提问。
```

```text
稀疏输入初始图
                                  ┌─ [🔴 证据 {缺少日志/schema}]
                                  ├─ [🔴 Schema 契约 {未知}]
[🔴 文件 A 生产者 {未知}] -> [🔴 文件 A 产物 {格式可疑}] -> [🔴 特性 2 解析器 {直接症状}]
                                  ├─ [🔴 时序/就绪 {未知}]
                                  └─ [🔴 契约测试 {未知/缺失}]
```

## 0.2 证据保真度示例

推演前不要只在“读代码”和“纯逻辑”之间二选一。先判断当前能拿到哪一层证据，并在地图中标注证据层级：

```text
证据保真度阶梯
[🟢 真实目标流程 {最高保真；可用则优先}]
   -> [🟢 等价运行/部署环境 {目标环境不可用时}]
      -> [🟢 DT/自动化验证 {覆盖关键转换}]
         -> [🟢 片段化执行/CLI 化探针 {隔离核心函数或协议}]
            -> [🟢 日志/产物回放 {复用既有运行事实}]
               -> [🟢 源码/schema/契约静态追踪]
                  -> [🔴 纯逻辑推演 {仅在前面证据不可得时；标明缺口}]
```

如果完整系统必须部署到指定环境才可运行，但当前处于开发机，不要直接写“无法验证”。应先判断是否能构造等价证据：

```text
目标环境不可用时的替代证明
[🔴 指定环境真实流程 {当前不可访问}]
   ├─ [🟢 DT/自动化测试 {覆盖核心输入->输出转换}]
   ├─ [🟢 片段执行 {直接运行关键解析/调度/校验逻辑}]
   ├─ [🟢 CLI 化探针 {模拟外部调用或状态查询}]
   ├─ [🟢 日志/产物回放 {使用历史真实结果}]
   └─ [🔴 剩余缺口 {部署环境时序/权限/资源差异需后续证明}]
```

## 1. 标记和注释放置

把红绿灯放在节点名前。把注释放在节点后方的 `{}` 中。

```text
[🔴 文件 A 生成器 {根因? schema 不匹配}]
[🔴 特性 2 解析器 {直接症状}]
[🟢 存储路径 {已验证可写}]
[🔴 就绪信号 {消费者读取前缺失}]
```

注释常见用途：

| 注释类型 | 放置位置 | 示例 |
| --- | --- | --- |
| 直接症状 | 报错出现的节点 | `[🔴 特性 2 解析器 {直接症状: 格式错误}]` |
| 根因候选 | 可能创建坏状态的上游节点 | `[🔴 文件 A 生成器 {根因? schema 无效}]` |
| 已确认根因 | 已证明创建坏状态的上游节点 | `[🔴 文件 A 生成器 {根因: 写 v1，消费者期望 v2}]` |
| 时序风险 | 顺序可能破坏正确性的节点或箭头 | `[🔴 消费者读取 {提交前读取}]` |
| 契约缺失 | 生产者/消费者契约负责人 | `[🔴 文件 A schema {负责人不清}]` |
| 证据 | 有证据或缺证据的节点 | `[🟢 存储路径 {日志 #42 已验证}]` |
| 边界 | 有意排除范围或已证明健康的节点 | `[🟢 鉴权检查 {GREEN boundary}]` |

注释要短。长解释放在图后说明中，地图中只保留短标签。

## 2. 何时下钻

当节点是 `🔴` 且满足以下任一条件时，进行纵向下钻：

- 节点隐藏多个内部职责。
- 直接症状和根本关联可能不同。
- 节点跨越异步边界。
- 节点拥有生成物、schema、契约、状态转换或调度决策。
- 节点过于含糊，无法支撑动作。
- 节点是缺少证据的关键假设。

不要下钻 `🟢` 节点，除非它是另一个 RED 依赖的边界且需要证明。

示例：

```text
Level0
[🟢 用户点击导出]
   -> [🔴 导出工作流 {格式错误稍后出现}]
      -> [🔴 特性 2 读取文件 A {直接症状}]

决策：下钻 [🔴 导出工作流]，因为它隐藏了生产者、生成物、就绪信号和消费者职责。

Level1 下钻: [🔴 导出工作流]
[🟢 用户命令已捕获]
   -> [🔴 特性 1 生成文件 A {根因?}]
      -> [🔴 文件 A schema {契约不清}]
         -> [🔴 文件 A 写入 {持久性未知}]
            -> [🔴 就绪通知 {缺失?}]
               -> [🔴 特性 2 读取文件 A {直接症状}]
```

## 3. 何时横向扩散

当 RED 节点会被主链路之外的相邻关注点影响时，进行横向扩散。

适合横向扩散的区域：

- 上游输入和配置。
- 下游消费者。
- 共享文件、缓存、队列、存储、会话、凭据或临时目录。
- 权限、安全、兼容性、迁移、国际化、日志、测试和可观测性。
- 调度、队列顺序、重试、取消、清理和生命周期钩子。

示例：

```text
Level1 主链路
[🔴 特性 1 生成文件 A {根因?}]
   -> [🔴 文件 A schema {契约不清}]
      -> [🔴 特性 2 解析器 {直接症状}]

从 [🔴 文件 A schema] 横向扩散
   ├─ [🔴 Schema 版本来源 {缺少负责人}]
   ├─ [🔴 兼容规则 {v1/v2 未定义}]
   ├─ [🟢 文件位置 {已验证同一路径}]
   └─ [🔴 契约测试 {缺少生产者-消费者测试}]
```

决策：从 `[🔴 文件 A schema]` 扩散，因为格式错误常由 schema 所有权、兼容性和缺失契约测试造成，而不是解析器本身造成。

## 4. 何时增加、删除、拆分或合并节点

地图应在循环中演化。

需要增加节点的情况：

- MECE 覆盖不完整。
- 某个缺失依赖可以解释 RED 标记。
- 时序分析暴露隐藏阶段，如提交、就绪、清理或重试。

需要删除节点的情况：

- 节点超出所选边界。
- 节点重复且没有增加职责。
- 证据证明节点无法影响当前链路。

需要拆分节点的情况：

- 节点混合生产者和消费者职责。
- 节点合并了数据创建、校验、持久化和消费。
- 节点同时隐藏直接症状和根本关联。

需要合并节点的情况：

- 多个标签描述同一职责且证据相同。
- 分开的节点制造虚假复杂度，却没有提升可行动性。

不要输出 Mutation Log；把变更后的结构直接体现在下一轮地图里。示例：

```text
上一轮
[🔴 导出工作流 {格式错误稍后出现}]

下一轮
[🔴 特性 1 生成器 {根因?}]
   -> [🔴 文件 A schema {契约不清}]
      -> [🔴 文件 A 提交 {持久性未知}]
         -> [🔴 就绪信号 {缺失}]
            -> [🔴 特性 2 解析器 {直接症状}]

从 [🔴 文件 A 提交] 横向扩散
   └─ [🟢 存储路径 {日志确认绝对路径一致}]
```

## 5. 完整 problem-location 示例

用户案例：`特性 1 生成文件 A。特性 2 读取文件 A 后报告格式错误。`

### 第 1 轮: Level0

```text
Level0 故障全景
[🟢 用户启动工作流]
   -> [🔴 特性 1 生成文件 A {根因? 未检查}]
      -> [🔴 文件 A 交接 {契约/时序未知}]
         -> [🔴 特性 2 读取文件 A {直接症状: 格式错误}]
            -> [🔴 用户看到失败 {表面症状}]
```

标记原因：

- `[🟢 用户启动工作流]`：触发已知，不能解释格式不匹配。
- `[🔴 特性 1 生成文件 A]`：生产者可能创建无效格式，因此是根因候选。
- `[🔴 文件 A 交接]`：交接混合 schema、写入完成和就绪信号，必须拆分。
- `[🔴 特性 2 读取文件 A]`：直接症状出现在这里，但它未必是根因。

下一步：下钻 `[🔴 文件 A 交接]`，因为它不满足 MECE，并隐藏异步阶段。

### 第 2 轮: 拆分并下钻

```text
Level1 下钻: 文件 A 交接
[🔴 特性 1 生成器 {根因?}]
   -> [🔴 文件 A schema {生产者/消费者契约不清}]
      -> [🔴 文件 A 校验 {写入前缺失}]
         -> [🔴 文件 A 写入 {持久性未知}]
            -> [🔴 就绪信号 {缺失}]
               -> [🔴 特性 2 解析器 {直接症状}]
```

图内变更说明：

```text
[🔴 文件 A 交接 {宽泛节点}]
   -> [🔴 文件 A schema {拆分: 契约}]
   -> [🔴 文件 A 校验 {拆分: 写入前验证}]
   -> [🔴 文件 A 写入 {拆分: 持久化}]
   -> [🔴 就绪信号 {拆分: 生产者/消费者交接}]
   -> [🔴 特性 2 解析器 {直接症状}]
```

下一步：从 `[🔴 文件 A schema]` 和 `[🔴 就绪信号]` 横向扩散，因为 schema 和就绪信号同时影响生产者与消费者。

### 第 3 轮: 横向扩散

```text
Level1 横向扩散后
[🔴 特性 1 生成器 {根因?}]
   -> [🔴 文件 A schema {契约不清}]
      ├─ [🔴 Schema 版本负责人 {缺失}]
      ├─ [🔴 向后兼容 {未定义}]
      └─ [🔴 契约测试 {缺失}]
   -> [🔴 文件 A 校验 {写入前缺失}]
   -> [🔴 文件 A 写入 {持久性未知}]
      ├─ [🟢 存储路径 {已验证同一路径}]
      └─ [🔴 原子写入 {未验证}]
   -> [🔴 就绪信号 {缺失}]
      ├─ [🔴 提交前发出事件 {可能竞态}]
      └─ [🔴 消费者重试 {未定义}]
   -> [🔴 特性 2 解析器 {直接症状}]
```

图内变更说明：

```text
[🔴 文件 A schema {契约不清}]
   ├─ [🔴 Schema 版本负责人 {缺失}]
   ├─ [🔴 向后兼容 {未定义}]
   └─ [🔴 契约测试 {缺失}]
[🔴 文件 A 写入 {持久性未知}]
   ├─ [🟢 存储路径 {已验证同一路径}]
   └─ [🔴 原子写入 {未验证}]
[🔴 就绪信号 {缺失}]
   ├─ [🔴 提交前发出事件 {可能竞态}]
   └─ [🔴 消费者重试 {未定义}]
```

下一步：增加时序透镜，因为就绪信号和原子写入仍是 RED。

### 第 4 轮: 时序透镜

```text
时序透镜
t0 [🟢 工作流开始]
t1 [🔴 特性 1 开始生成文件 A]
t2 [🔴 特性 1 发出就绪事件 {提交前?}]
t3 [🔴 特性 2 读取文件 A {直接症状: 部分内容/错误格式}]
t4 [🔴 文件 A 提交完成 {晚于 t3}]
t5 [🔴 用户看到格式错误]
```

图内变更说明：

```text
t1 [🔴 特性 1 开始生成文件 A]
t2 [🔴 提交前就绪事件 {新增时序节点}]
t3 [🔴 特性 2 读取文件 A {直接症状: 部分内容/错误格式}]
t4 [🔴 文件 A 提交完成 {晚于 t3}]
```

最终解释：

- Direct RED: `[🔴 特性 2 解析器 {直接症状}]`。
- Root RED candidates: `[🔴 特性 1 生成器]`、`[🔴 文件 A schema]`、`[🔴 就绪信号]`、`[🔴 提交前发出事件]`。
- GREEN boundary: `[🟢 存储路径]`、`[🟢 工作流开始]`。
- 最有价值的下一步证明：比较 t2/t3/t4 时刻的文件 A 内容，并验证就绪信号是否在持久化提交后发出。

## 6. 完整 feature-panorama 示例

用户案例：`设计一个新的诊断面板，用于消费生成的诊断产物。`

### 第 1 轮: Level0 特性图

```text
Level0 特性全景
[🟢 用户打开诊断]
   -> [🔴 诊断运行触发 {新动作}]
      -> [🔴 产物生成器 {根本能力}]
         -> [🔴 产物 schema {契约缺失}]
            -> [🔴 就绪信号 {缺失}]
               -> [🔴 面板渲染器 {直接能力}]
                  -> [🟢 用户反馈区域 {既有 UI 模式}]
```

决策：下钻 `[🔴 产物生成器]`，因为它拥有根本能力。稍后扩散 `[🔴 面板渲染器]`，因为它是直接消费者界面。

### 第 2 轮: 根本能力下钻

```text
Level1 下钻: 产物生成器
[🔴 运行上下文收集 {输入未定义}]
   -> [🔴 诊断执行 {命令契约缺失}]
      -> [🔴 产物 schema {版本 + 负责人缺失}]
         -> [🔴 产物写入 {原子性未说明}]
            -> [🔴 就绪信号 {消费者交接缺失}]
```

图内变更说明：

```text
[🔴 产物生成器 {宽泛节点}]
   -> [🔴 运行上下文收集 {输入未定义}]
      -> [🔴 诊断执行 {命令契约缺失}]
         -> [🔴 产物 schema {版本 + 负责人缺失}]
            -> [🔴 产物写入 {原子性未说明}]
               -> [🔴 就绪信号 {消费者交接缺失}]
```

### 第 3 轮: 直接消费者扩散

```text
从 [🔴 面板渲染器 {直接能力}] 横向扩散
   ├─ [🔴 空状态 {产物缺失}]
   ├─ [🔴 解析错误状态 {产物格式错误}]
   ├─ [🔴 加载状态 {等待就绪信号}]
   ├─ [🔴 刷新/重试 {未设计}]
   ├─ [🟢 布局外壳 {既有组件}]
   └─ [🔴 i18n 文案键 {必需}]
```

决策：横向扩散，因为即使产物契约修好，渲染器正确性仍依赖 UX 状态、就绪信号、重试和 i18n。

### 第 4 轮: Final Feature Panorama Map

```text
Final Feature Panorama Map
[🟢 用户打开诊断]
   -> [🔴 诊断运行触发 {新动作}]
      -> [🔴 运行上下文收集 {输入未定义}]
         -> [🔴 诊断执行 {命令契约缺失}]
            -> [🔴 产物 schema {根本能力: 版本 + 负责人缺失}]
               ├─ [🔴 契约测试 {缺少生产者-消费者证明}]
               └─ [🔴 兼容规则 {迁移未定义}]
            -> [🔴 产物写入 {原子性未说明}]
               └─ [🔴 就绪信号 {消费者交接缺失}]
                  -> [🔴 面板渲染器 {直接能力}]
                     ├─ [🔴 加载状态 {等待就绪信号}]
                     ├─ [🔴 解析错误状态 {产物格式错误}]
                     ├─ [🔴 刷新/重试 {未设计}]
                     ├─ [🔴 i18n 文案键 {必需}]
                     └─ [🟢 布局外壳 {复用既有组件}]
```

最终解释：

- Root capability RED: 产物 schema、生成器契约、原子写入、就绪信号。
- Direct capability RED: 面板渲染状态和重试行为。
- GREEN reuse: 用户入口和布局外壳。
- 第一证明点：创建生产者-消费者契约测试，生成产物、等待就绪信号，然后从该产物渲染面板。

## 7. 快速决策规则

画图时使用这些快速规则：

| 情况 | 动作 |
| --- | --- |
| RED 节点宽泛或含糊 | 下钻。 |
| RED 节点有上游生产者和下游消费者 | 拆分为生产者、生成物/契约、就绪信号、消费者。 |
| 错误出现在消费者 | 标记消费者 `{直接症状}`，并向上游追踪 `{根因?}`。 |
| 涉及生成文件/数据/事件 | 增加 schema、校验、提交、就绪信号和消费者读取节点。 |
| 节点单独正确但整体行为失败 | 增加时序透镜。 |
| 分支共享状态/配置/权限/日志/测试 | 横向扩散。 |
| 兄弟节点重叠 | 拆分或重命名，直到满足 MECE。 |
| 证据证明边界健康 | 用 `🟢` 标记并附 `{GREEN boundary}` 或具体证据。 |
| 证据缺失但重要 | 先选择当前可获得的最高保真证据；仍缺失时用 `🔴` 标记并附 `{缺失证据: 需要哪类证明}`。 |
| 用户输入不完整 | 默认不提问；添加 RED 未知/证据节点并继续。 |
| 找到第一个可能根因 | 不要停止；先边界化兄弟分支。 |
| 地图只有一条线 | 增加上游、下游、共享状态、时序、可观测性和测试分支。 |
