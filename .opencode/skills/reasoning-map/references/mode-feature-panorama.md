# Mode: feature-panorama

当任务需要设计或评估特性、缺失能力、工作流新增、产品界面、架构变更或实现方案时，使用此模式。

## 目标

产出特性全景，展示：

- 完整顶层能力链路。
- 可复用的既有能力。
- 缺失能力和设计缺口。
- 依赖与相邻影响面。
- 实现优先级和证明点。
- 最终特性全景必须是带红/绿标记和内联注释的 ASCII map，并把注释放在缺失、风险或可复用能力位置。

即使产品细节不完整，也要开始，但不要把可获得或可构造的证据直接遗留。缺失的 UX 决策、契约、负责人、API、测试或发布约束，应先选择当前可用的最高保真证据：真实产品流、等价原型/运行环境、DT/自动化验证、片段化执行、CLI 化探针、日志/产物读取、配置/schema/契约检查、既有实现和相邻模块追踪。只有这些证据不可得、需要用户业务决策、风险过高或超出当前权限时，才作为图中的 `🔴` 能力节点，而不是开始前的阻塞项。

## 证据保真度规则

在绘制或更新特性全景前，先对可验证未知选择最高保真的可获得证据：

1. 先判断该能力最终要在哪个目标链路中成立，以及当前能接近该链路到什么程度。
2. 完整产品或运行环境可用时，优先观察真实能力链路和真实反馈。
3. 完整目标环境不可用时，主动构造等价验证：可交互原型、DT/自动化测试、模块级执行、协议或数据片段执行、CLI 化探针、日志/产物回放、schema/契约校验。
4. 只有运行或替代验证不可得时，才退到源码静态追踪、文档和规则检查；逻辑推演必须标出证据保真度不足。
5. 把证据结果回写到地图；只有证据选择并尝试后仍需要用户决策或不可访问的内容才能保留为 `🔴` 未闭环节点。
6. 如果用户要求“确认后再行动”，仍允许不会改变目标系统状态的证据收集和替代验证；禁止的是实现、写业务文件、破坏性运行或未经确认的高风险动作。

## Level0 链路模式

把 Level0 构造成该特性的端到端能力图。除非每个侧向分支都已明确边界化，否则不要把 Level0 限制为单链路。常见模式：

| 特性类型 | Level0 链路示例 |
| --- | --- |
| 用户界面特性 | 入口 -> 用户意图捕获 -> 状态/模型 -> 动作执行 -> 反馈 -> 持久化/历史 |
| 开发者工具特性 | 命令/API -> 上下文发现 -> 规划 -> 执行 -> 验证 -> 产物/报告 |
| 集成特性 | 配置 -> 凭据/权限 -> 协议适配 -> 运行时执行 -> 诊断 -> 恢复 |
| 工作流特性 | 触发 -> 阶段编排 -> 人工评审/审批 -> 自动化 -> 结果跟踪 -> 审计轨迹 |
| 数据特性 | 来源 -> 校验 -> 转换 -> 存储/索引 -> 查询/视图 -> 导出/消费者 |

如果特性较新，Level0 可以包含概念节点。未实现或未定义节点标为 `RED`。

feature-panorama 的 Level0 通常应包含：

```text
特性图分支
                                      ┌─ [UX 状态/反馈]
                                      ├─ [权限/安全/配置]
[用户/系统触发] -> [核心能力路径] -> [消费者/结果/产物]
                                      ├─ [共享契约/schema/状态]
                                      ├─ [时序/编排/生命周期]
                                       └─ [验证/测试/替代证明/可观测性]
```

先画 Level0 ASCII map。示例：

```text
Level0 特性全景
[🟢 入口]
   -> [🔴 意图捕获 {UX 未定义}]
      -> [🔴 编排 {新能力}]
         -> [🔴 产物生成 {需要 schema 负责人}]
            -> [🔴 就绪信号 {缺失}]
               -> [🟢 反馈/历史 {复用既有视图}]

从 [🔴 编排] 横向扩散
   ├─ [🔴 权限检查 {需要策略}]
   ├─ [🔴 诊断能力 {缺少日志 + 验证器}]
   └─ [🟢 既有任务运行器 {复用}]
```

如需更完整的地图示例，包括节点变更、能力缺口和时序注释，读取 `references/map-examples.md`。

## 标记规则

当能力已经存在、设计足够充分或有清晰复用实现路径时，标记 `GREEN`。

满足以下任一条件时标记 `RED`：

- 能力缺失。
- 用户体验未定义。
- 技术负责人或模块不清晰。
- 数据契约或 API 缺失。
- 权限、安全、可靠性、可观测性、国际化、测试或迁移影响未解决。
- 节点依赖未验证假设。
- 实现可行但没有证明点。

## 纵向下钻

对每个 RED 能力，拆解为：

1. 用户目标或系统职责。
2. 输入和输出契约。
3. 状态模型和生命周期。
4. API/IPC/模块边界。
5. 错误、空状态、加载、取消和重试状态。
6. 安全、权限和隐私考量。
7. 可观测性、验证和测试。
8. 文档或运维交接。
9. 生成文件、产物、事件或状态的生产者/消费者所有权。
10. 执行顺序、就绪信号和异步协调。

然后给每个子节点标记 RED/GREEN。

## MECE 特性分解

每一层特性分解都要保持 MECE，一次只沿一个主轴拆分：

| 拆分轴 | 使用场景 |
| --- | --- |
| 用户旅程阶段 | 入口、配置、执行、反馈、历史、恢复。 |
| 技术职责 | UI、桥接/API、编排、领域服务、持久化、外部集成、验证。 |
| 数据生命周期 | 创建、校验、序列化、持久化、发出就绪信号、消费、迁移、删除。 |
| 工程质量 | 权限、可观测性、可靠性、性能、兼容性、测试、文档。 |

除非报告明确解释边界，否则不要在兄弟节点中混合多个拆分轴。如果某个能力出现在两个位置，只定义一次负责人，并在消费者侧引用。

## 直接能力 vs 根本能力

在特性设计中，缺失行为可能出现在消费界面，但真正缺失能力属于上游。

示例：如果 `特性 2` 需要展示 `文件 A`，但格式不稳定，直接缺失能力可能看起来是 `特性 2 解析容错`，而根本缺失能力可能是 `特性 1 文件 A schema 契约和生成器校验`。

始终识别：

| 字段 | 含义 |
| --- | --- |
| 直接能力 | 用户或消费模块需要行为的表面。 |
| 根本能力 | 必须使行为可靠的生产者、契约、调度器或生命周期负责人。 |
| 转换证明 | 将 root RED 转为 GREEN 的验证。 |

## 时序与调度设计

对跨多个步骤或异步边界的特性，定义预期顺序：

```text
[🟢 触发]
   -> [🔴 生产者开始 {负责人?}]
      -> [🔴 输出已校验 {schema?}]
         -> [🔴 输出已提交 {持久性?}]
            -> [🔴 就绪信号已发出 {缺失?}]
               -> [🔴 消费者读取 {顺序?}]
                  -> [🔴 消费者确认/使用完成 {幂等性?}]
                     -> [🟢 清理/历史]
```

当设计未说明就绪、顺序、幂等性、取消、重试、陈旧状态处理，或消费者早于生产者完成时应如何处理时，把时序标为 `RED`。

当时序影响正确性时，用 ASCII 时间线表示调度：

```text
特性时序透镜
t0 [🟢 用户启动特性]
t1 [🔴 生产者已调度]
t2 [🔴 消费者已启用 {早于就绪信号}]
t3 [🔴 输出已提交]
t4 [🔴 就绪信号发出过晚]
```

## 横向扩散

标记一个层级后，从每个 RED 节点横向扩散：

| 扩散区域 | 问题 |
| --- | --- |
| 上游触发 | 什么用户意图、事件、命令或系统条件启动该能力？ |
| 下游消费者 | 哪个 UI、服务、报告、产物或工作流消费结果？ |
| 共享契约 | 是否影响类型、schema、IPC 通道、CLI 参数、配置键或持久化格式？ |
| 生产者/消费者 | 哪个特性创建每个产物或状态，哪个特性消费它？格式兼容负责人是否明确？ |
| 调度 | 预期执行顺序是什么？什么机制防止竞态、陈旧读取、过早清理或过晚通知？ |
| 横切质量 | 国际化、可访问性、安全、隐私、性能、诊断和可靠性是否覆盖？ |
| 既有复用 | 哪些现有模块可通过复用变成 GREEN，而不是新增实现？ |
| 验证 | 哪个真实流程、等价环境、DT/自动化测试、片段执行、CLI 化探针、演示、日志/产物或契约检查能证明能力完成？ |

## 特性全景结论

结尾包含这些类别：

- `Existing GREEN`：已存在、可复用能力。
- `Missing RED`：必须设计或实现的能力。
- `Risk RED`：可能阻塞交付的假设、依赖或横切关注点。
- `Boundary GREEN`：有意排除范围或已覆盖区域。

同时包含最终 `Feature Panorama Map`，并把缺失能力、根本能力、直接能力、时序风险和可复用 GREEN 注释放在 ASCII 图内的对应节点上。

## 推荐动作

按依赖和证明优先级排序：

1. 先定义契约，再定义实现细节。
2. 先闭环用户流 RED 节点，再做内部优化。
3. 先闭环安全、权限和数据生命周期 RED 节点，再广泛发布。
4. 为每个 RED-to-GREEN 转换添加当前可获得的最高保真验证证明。
5. 仅当边界理由明确时，才把范围外区域标为 GREEN。

不要在产出第一张全景图前向用户索要缺失产品或实现细节。先选择并尝试当前可获得的最高保真证据；真实或替代证据仍需要用户决策或不可得的细节，才作为带验证/设计动作的 `🔴` 能力或证据节点放入图中。
