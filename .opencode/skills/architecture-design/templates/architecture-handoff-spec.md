## 一、组件边界

每个组件必须对应模型中的一个元素,职责与模型 description 一致。

| 组件（FQN） | 显示名 | 归属环 | 职责 | 禁止越界 | 模型依据 | 置信度 |
| --- | --- | --- | --- | --- | --- | --- |
| | | SRC 内部位置 | | | 元素 id | % |

**填写规则**

- 「禁止越界」写该组件**不应承担**的职责,用于实现时防止职责漂移
- 「模型依据」必须填元素 id;写不出则该行置信度不得高于 50%
- 未在模型中出现的组件不得写入本表

## 二、依赖约束

**F 侧功能边界是依赖方向的依据**——先说允许哪些组件互相依赖,再说实际依赖了什么。

| Feature 功能单元 | 允许的依赖方向 | 禁止反向 | 模型依据 |
| --- | --- | --- | --- |
| F-00X |可依赖 <范围> | 是 | US → F 边 |

实际依赖清单：

| From | To | 关系 | 类型 | 禁止反向 | 模型依据 |
| --- | --- | --- | --- | --- | --- |
| | | 同步 / 异步 | 强约束 / 弱约束 | 是 / 否 | `.depends` 边 |

**填写规则**

- **先填 F 侧功能边界**：没有它,「谁调谁」只是现状描述,不是约束
- 方向必须与模型一致:模型 `a .depends b` 表示 a 调用 b
- 「禁止反向」为「是」时,实现阶段不得引入反向依赖
- 与外部系统的依赖需标注凭据边界(由谁提供、存放在哪)
- 模型中未出现的依赖关系不得写入本表

## 三、流程锚点

流程来自 I 环的 `dynamic view`。**主干与分支须分别列出**——分支是独立视图，不是主干的可选项。

| 类型 | 流程 | 视图 id | 关键步骤 | 参与组件 |
| --- | --- | --- | --- | --- |
| 主干 / 分支 | | | | |

**填写规则**

- 视图 id 必须真实存在于模型中,可被 MCP 的 `read-view` 读取
- **主干视图必须列出**,它是「本次交付首次可演示」的最小路径
- 当前 LikeC4 版本不支持条件分支与异常块(见 `03-dynamic-views.md`),这类流程按 `09-likec4-substitutions.md` 拆成多个 LikeC4 视图,此处列出全部视图 id
- 每条流程锚点应能被实现方用于定位代码改动范围

## 五、验收锚点

**NF 侧的可度量值是验收依据**——没有它,「怎样算完成」是空的。

| NF 项 | 可度量值 | 约束的 US | 验收方式 | 模型依据 |
| --- | --- | --- | --- | --- |
| NF-00X | | US-00X | | `NF → US` 边 |

**填写规则**

- **每个 NF 项都要出现在本表**,并标明它约束哪条 US（`NF → US` 的 `.trace` 边）
- NF 侧为空时须显式写「本次交付无质量约束」并说明理由,不能沉默跳过
- 验收信号必须可观察或有明确查询方式
- 不接受「符合设计文档」这类无法验证的表述
