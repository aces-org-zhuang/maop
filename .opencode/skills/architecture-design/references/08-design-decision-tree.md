# SOP 08 - 设计作业决策树（AI 引导流程）

## 目的

`07-seven-layer-design.md` 定义了**每层该产出什么**。本 SOP 定义 **AI 在设计过程中每一步该怎么问、给什么候选、什么时候必须停下来等用户确认**。

没有这一步，AI 会一次性把七层全部写完交给用户——用户看不懂，也无法在关键业务判断上纠偏。设计是最需要人类介入的环节，AI 的角色是**给候选和推荐**，而不是替用户做业务决定。

## 分工原则（贯穿全流程）

| 角色 | 负责 |
| --- | --- |
| **AI** | 产出候选方案、给出推荐值与推荐理由、指出风险与缺口、问出用户没想到的问题 |
| **用户** | 确认业务判断、裁决多选一、给出可度量的目标值、决定范围与优先级 |

**AI 不得代替用户做业务决定。** 下面每个节点标了 `⏸` 的是**必须停下等确认**的点，其余节点 AI 可推进但要在交付时说明假设。

---

## 节点 0 · 规模判定（⏸ 入口必问）

**先判断这个需求要不要走完整七层。** 判错方向都会浪费时间：小的走七层是过度工程，大的走轻量路径会漏设计。

| 判定 | 特征 | 路径 |
| --- | --- | --- |
| **完整七层** | 新功能模块 / 新用户角色 / 跨多个现有模块 / 有明确 UI 交互 / 引入新的外部依赖 | 走节点 1-6 |
| **局部补充** | 已有模块加一个字段 / 改一处校验规则 / 修一个缺陷 | 只更新受影响的层，说明为何其余层不动 |
| **架构变更** | 依赖方向变化 / 部署形态变化 / 新增外部系统 | 先 `07` 判断影响面，再决定是否需要七层 |
| **仅表达** | 只要一张图，不改模型事实 | 转 `expression-delivery` |

**AI 必须问的**：

1. 这次改动是否引入新的用户角色或新的用户可见行为？
2. 是否跨越现有模块边界？
3. 有没有新的外部依赖（第三方服务、支付、通知）？
4. 业务方是否需要评审这份设计？

用户回答后**明确告知走哪条路径**，并说明理由。不得默默跳层。

---

## 节点 1 · US 用户故事（⏸ 停下确认）

**AI 的动作**：基于原始需求，草拟 3-5 条候选用户故事，每条包含角色、场景、期望、验收标准。

**输出格式**：

```text
US-001 <标题>
  角色：<谁>
  场景：<什么情况下>
  期望：<要达成什么>
  验收：<怎样算完成，必须可判定>
```

**⏸ 必须问用户**：

- 这几条是否覆盖了真实诉求？有没有 AI 没识别出的场景？
- 哪些是本期必做，哪些可以延后？（影响 F 层的范围）
- 验收标准里有没有业务方特有的规则（内部口径、审批流、例外情况）？

**不要**：一次性只给一条故事让用户确认到底。给候选集让用户裁剪，比让用户从零描述快得多。

**校准提示**：验收标准必须可判定。「体验流畅」不可判定，「提交后 2 秒内返回结果」可判定。AI 发现用户给的验收标准不可判定时，应当指出并给出可判定的改写建议。

---

## 节点 2 · F 功能框架 + NF 非功能框架（⏸ 停下确认）

### F 层

**AI 的动作**：把选定的 US 归并为功能单元，每个功能单元下挂它服务的 US。

**⏸ 必须问用户**：

- 功能边界对不对？有没有把两个功能混成一个，或把一个拆成两个？
- 有没有遗漏的功能？
- 功能之间是并列还是有依赖？

### NF 层（这一层最容易做错）

**AI 的动作**：针对每个 F 项，给出**可度量的推荐值 + 推荐理由**。理由必须引用来源：行业惯例、现有系统的实际值、用户的业务约束。

**必须问用户**：

- 推荐值是否符合业务预期？业务能接受多少？
- 有没有 AI 没列出的质量维度？（合规、风控、审计、留存……）
- 冲突时怎么取舍？（例如一致性 vs 延迟）

**NF 项的三种结局，必须标明是哪一种**：

| 类型 | 处理 |
| --- | --- |
| 已确认 | 用户给出具体值 → 写入模型 |
| 待补充 | 用户无法确定 → 记入缺口清单，**不编造** |
| 不适用 | 该功能确实无此要求 → 显式标注「不适用」及理由 |

**禁止**：把「系统要快」「体验要好」这类不可度量表述直接写进 NF 层。**禁止**：用户没给值时 AI 自己定一个然后当作已确认。

---

## 节点 3 · I 实现层（不含源码）

**AI 的动作**：产出三类内容，全部不含源码。

| 产出 | 内容 | 工具 |
| --- | --- | --- |
| 业务目标 | 该功能要达成的业务结果 | 文字描述 |
| 业务状态 | 业务对象的生命周期状态机 | **Mermaid `stateDiagram-v2`** |
| 业务步骤 | 达成目标的操作序列，含参与角色 | LikeC4 `dynamic view` |

**⏸ 必须问用户**：

- 状态是否完整？有没有漏掉异常态、取消态、超时态？
- 状态迁移的**触发条件**是什么？谁来触发？
- 步骤里有没有需要人工介入的环节？
- 一个流程有没有分支？分支的判断依据是什么？

**关于分支**：LikeC4 1.58.0 不支持 `opt` / `loop` / `alt` / `try`。**含分支的流程用 Mermaid flowchart**，不要在 LikeC4 里硬凑。

**本层禁止出现**：类名、函数名、表名、文件名。出现即为越界，应引导到 SRC 层。

---

## 节点 4 · UI 界面层（⏸ 停下确认）

### 交互设计

**AI 的动作**：对每个用户操作，给出「触发什么 → 系统反馈什么 → 失败怎么回退 → 可否撤销」。

**⏸ 必须问用户**：

- 失败时用户看到什么？他们的下一步是什么？
- 有没有需要二次确认的破坏性操作？
- 等待时间较长时怎么反馈？

### 信息设计

**AI 的动作**：列出字段、列表区、可见区域、筛选区域、扩展功能（通知 / 导出 / 批量操作）。

**必须覆盖四种状态**，缺一即不完整：

| 状态 | 为什么必须有 |
| --- | --- |
| 空状态 | 新用户第一次进来看到什么 |
| 加载状态 | 慢操作时的反馈 |
| 错误状态 | 失败时的可读信息与恢复动作 |
| 无权限状态 | 权限不足时的表现 |

**⏸ 必须问用户**：

- 哪些字段是决策必需的？哪些只是参考？
- 筛选条件通常怎么组合？
- 有没有需要用户特别关注的异常数据？
- 是否需要导出？导出什么内容，谁能看到？

## 节点 5 · SRC 源码层（先读代码，不猜）

**AI 的动作顺序不能颠倒**：

```text
1. 读真实代码结构（目录、入口文件、既有模块）
2. 把 I 层的业务步骤映射到实际文件
3. 标注哪些是新增、哪些是修改、哪些禁止触碰
4. 无法对应的标记为 待补充，不编造路径
```

**⏸ 必须问用户**：

- 新代码放在哪里？（新文件还是既有文件内）
- 哪些目录是禁止触碰的？
- 有没有既有的相似实现可以复用？
- 技术选型有既定约束吗？

**禁止**：没读代码就给出文件路径。**禁止**：把设计里没有的路径写出来充数。

**产出必须包含**：组件划分、依赖方向、类设计（PlantUML）、时序、数据流。

---

## 节点 6 · 缺口盘点与用户确认（⏸ 收尾必做）

设计收尾**必须**输出一份缺口清单，不得因为「看起来完整」而跳过。

### 缺口清单格式

```text
待用户确认：
- [业务判断] <具体问题> — 影响：<哪一层>
- [目标值]   <NF 项缺可度量值> — 建议：<推荐值及理由>

待补充：
- [源码路径] <I 步骤找不到对应文件> — 需要：<确认是否新建>
- [外部依赖] <第三方接口行为未知> — 需要：<文档或沙箱验证>

未覆盖：
- <明确说明哪些内容本次未设计及原因>
```

### 必须主动提出的问题

这些是 AI 最容易漏、但会后悔的：

- 有没有异常路径没设计？（网络失败、超时、并发冲突）
- 数据量增长后，这个设计还成立吗？
- 有没有隐私或合规要求没覆盖？
- 这个功能上线后怎么验证成功？指标是什么？
- 有没有需要运营或客服了解的部分？（他们会在什么时候用到）

### 交付前的确认清单

- [ ] 走的是完整七层还是局部路径？理由已说明
- [ ] 每条 US 的链路完整性已核对，缺失层已列出
- [ ] 所有 NF 项都有明确结局（已确认 / 待补充 / 不适用）
- [ ] I 层无源码元素
- [ ] UI 层覆盖四种状态
- [ ] SRC 层路径已核对真实代码，未凭空编造
- [ ] 缺口清单已输出，且未用猜测填充
- [ ] 构建部署图未产出，或已说明为何此时产出

## 场景分支：不必走完七层的情况

| 场景 | 走哪些层 | 说明 |
| --- | --- | --- |
| 已有模块加字段 | SRC + 交接 | F/NF/I/UI 通常不动，说明为何不动 |
| 改一处校验规则 | I（状态或步骤）+ SRC | 校验规则属业务逻辑，需业务确认 |
| 修缺陷 | SRC | 但需确认是否暴露了设计缺失 |
| 新增外部依赖 | F + NF + I + SRC | 外部依赖必然带来 NF 要求 |
| 仅改界面布局 | UI | SRC 不动，除非交互逻辑也变了 |
| 架构调整 | 全层 + 交接 | 先评估影响面再决定范围 |

**关键**：即使是局部路径，也必须说明**为什么其余层不需要改动**。跳过不等于不用管。

---

## 反模式（明确禁止）

| 反模式 | 为什么错 |
| --- | --- |
| 一次性输出七层全部内容 | 用户无法在关键判断上介入，错了要整体返工 |
| AI 自己定 NF 值然后当已确认 | 业务目标值是业务决策，不是技术判断 |
| I 层出现类名和表名 | 越界，且换技术栈就不成立 |
| SRC 层给没读过的文件路径 | 架构图与代码脱节，比不写更糟 |
| 跳过层但不说明 | 用户无法判断设计是否完整 |
| 缺口用「合理推测」填满 | 猜测会伪装成设计，后续难以发现 |
| 只问技术问题不问业务问题 | 业务规则只有用户知道 |
