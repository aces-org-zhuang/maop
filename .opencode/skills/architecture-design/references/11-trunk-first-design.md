# SOP 11 - 主干优先与视图分离（Trunk First）

## 目的

一张图里塞进主干、分支、异常、边界、外围需求，看起来"面面俱到"，实际是**无人能读**。评审时没人能指出问题，因为它太密；实现时没人敢动手，因为不知道从哪下手。

本 SOP 定义两件事：

1. **设计顺序**：先确认主干逻辑，再展开分支逻辑。
2. **视图粒度**：一张图只回答一个问题；分支独立成图。

这是**先决规则**，优先于 `00-diagram-routing.md` 的图类型选择与 `08-design-decision-tree.md` 的节点推进顺序。

## 三条硬规则

| # | 规则 | 违反后果 |
| --- | --- | --- |
| **T1 主干先行** | 任何视图先只画主干（happy path / 核心链路），主干经用户确认后才允许展开分支 | 主干没定就铺分支，最后发现主干本身错了，全盘返工 |
| **T2 一图一意图** | 一张视图只回答一个评审问题。超过容量上限必须拆 | 图变成"面面俱到实则混乱"，评审失效 |
| **T3 主干冻结** | 主干确认后进入分支阶段。分支阶段**只能新增视图**，不得修改主干模型 | 分支需求反向改写主干，主干不再是稳定的共识基线 |

---

## 一、主干先行（T1）

### 什么是主干

主干 = **在没有异常、没有边界、没有可选分支时，这件事怎么跑通**。

| 层 | 主干的样子 |
| --- | --- |
| US | 一句话故事，角色 + 场景 + 期望，不含例外 |
| F | 主干涉及的功能单元，不含"可选/增强/兼容"类功能 |
| I 步骤 | 从触发到结果的**单条**操作序列，只有必经步骤 |
| I 状态 | 主干上必经的状态，不含异常态与取消态 |
| UI | 主干操作的主反馈路径，不含错误提示与空状态 |
| SRC | 主干路径上的组件与调用，不含降级与补偿逻辑 |

### 主干确认门禁（⏸ 必停）

在展开任何分支前，必须输出并让用户确认：

```text
⏸ 主干确认（本轮只谈主干，分支先不展开）
主干路径：<触发> → <步骤1> → <步骤2> → <结果>
必经状态：<A> → <B> → <C>
主干边界：本次不展开的分支共 <N> 条，登记在分支清单
主干确认后：分支逐条展开，每条一个独立视图
```

**未确认主干就展开分支，是本技能最常见的返工来源。** 分支越多，主干越难被独立审视，最后没人说得清主干到底是什么。

### 分支登记而非展开

主干确认时，把识别到的分支**登记**为清单，不立即画图：

```text
分支清单（主干确认后逐条处理）
- BR-01 条件：库存不足        归属：I 步骤 / SRC    优先级：高
- BR-02 异常：支付网关超时    归属：I 状态 / SRC    优先级：高
- BR-03 循环：重试至上限      归属：I 步骤 / SRC    优先级：中
- BR-04 降级：RAGFlow 不可用  归属：SRC            优先级：中
- BR-05 外围：历史订单导出    归属：F / UI / SRC    优先级：低（非本期）
```

每条分支在展开前单独过一次门禁：**这条分支是否改变了主干语义？** 若改变，停下交用户裁决（见第三节）。

## 二、一图一意图（T2）

### 容量上限（超出即拆，不做例外）

| 视图类型 | 上限 | 超出后的拆法 |
| --- | --- | --- |
| element view | 12 个可见元素 | 按子域 / 按层拆；或主干图 + 分支图 |
| dynamic view（步骤 / 时序） | 8 步 或 10 条消息 | 每条路径一个视图 |
| 状态机视图 | 8 个状态 | 主干状态视图 + 异常/取消状态视图 |
| 信息设计视图 | 12 个关键字段 | 按区域（列表区 / 筛选区 / 详情区）拆 |
| 跨层链路视图 | 一个 US 的完整链路 | **只放主干链路**；分支链路另起视图 |

> 上限是**评审可用性**的经验阈值，不是语法限制。超限不报错，但会让人无法在一次阅读中抓住主干。

### 拆分原则

- **主干视图与分支视图分离**：主干视图 `include` 的元素集合中不得出现任何仅属于分支的元素。
- **分支视图只画增量**：分支视图 `include` 分支涉及的元素 + 主干的**接缝锚点**（分支从主干哪个节点岔出、在哪个节点合流），不重复主干全部步骤。
- **接缝锚点必须显式**：分支视图的 `description` 中写明"自 `<主干节点>` 岔出，合流至 `<主干节点>`"。读者不打开主干视图无法理解分支——这是可接受的，因为主干视图才是入口。
- **命名成对**：`impl-order-main` / `impl-order-branch-stock-short`，从名字就能看出归属与条件。

### 主干视图与分支视图的形态对照

```c4
views {
  // 主干：只有必经步骤
  dynamic view implOrderMain {
    variant sequence
    title '下单主干路径'
    description '从提交订单到支付确认的必经步骤，不含异常与可选分支。'
    include ui_submit, i_validate, i_pay, i_confirm
    ui_submit -> i_validate '提交订单'
    i_validate -> i_pay '校验通过'
    i_pay -> i_confirm '支付成功'
  }

  // 分支：只画增量 + 接缝锚点
  dynamic view implOrderBranchStockShort {
    variant sequence
    title '下单分支：库存不足'
    description '自「校验订单」节点岔出，合流至「下单失败」节点。'
    include i_validate, i_stockCheck, i_failed
    i_validate -> i_stockCheck '库存校验'
    i_stockCheck -> i_failed '库存不足'
  }
}
```

**注意**：两张图之间没有自动链接。读者从 `implOrderMain` 的 `description` 或导航入口找到分支清单，再进分支视图。

> 实测记录（likec4 1.58.0）：上述主干视图、分支视图，以及下方的 `exclude` 写法与 I 层状态的主干 / 分支视图拆分，全部 `✓ Valid (3 files)` 且 `build` 输出 `✓ all views layouted`。

### 主干视图的两种写法

**写法 A · 显式列举（动态视图 / 步骤类）**：只 `include` 主干元素，分支元素完全不出现。

**写法 B · 整体包含 + 排除（静态结构视图）**：模型里分支元素已存在时，用 `exclude` 把它们从主干视图剔除。实测通过：

```c4
views {
  view implOrderTrunkFiltered of i_validate {
    title '下单主干结构（排除分支元素）'
    description '主干视图用 exclude 排除分支专用元素，避免把分支塞进主干。'
    include *
    exclude i_stockCheck, i_failed
  }
}
```

**写法 B 的适用前提**：分支元素已写入模型。若分支尚未展开，用写法 A 显式列举，不要先写进模型再排除——那等于把分支事实提前固化。

> 实测记录（likec4 1.58.0）：写法 A、B 均 `✓ Valid` 且 `build` 通过。

## 三、主干冻结（T3）

### 冻结规则

主干确认后，主干相关的**元素、关系、视图**进入冻结状态：

| 分支阶段的动作 | 是否允许 |
| --- | --- |
| 新增分支专用元素与视图 | 允许 |
| 新增分支视图中的关系 | 允许 |
| 修改主干视图的 `include` 集合以加入分支元素 | **禁止** |
| 修改主干元素的关系或 `description` | **禁止**，必须走主干变更门禁 |
| 删除或重命名主干元素 | **禁止**，编号不复用 |

### 主干变更门禁（⏸ 必停）

分支展开过程中若发现主干必须改，**不得就地改**，输出：

```text
⏸ 主干变更请求
发现阶段：展开 BR-03 循环分支时
变更内容：主干「校验订单 → 发起支付」之间需要插入「锁定库存」
原因：不锁定时 BR-03 重试会造成超卖
影响：主干 I 步骤、SRC 组件依赖、NF-002 时延指标
请裁决：
  1. 接受，主干回退到 US 层重新确认后再展开分支
  2. 不接受，把 BR-03 边界化为「不支持重试」
用户确认后才继续。
```

**为什么必须停下**：分支开发者最容易犯的错是"顺手把主干补一下"。每一次"顺手"都会让主干失去共识——三个月后没人说得清主干到底是什么。

### 外围需求隔离

非本期的、外围的、锦上添花的需求（导出、批量操作、兼容旧版本）：

- **不进入主干视图**，也不进入本期分支视图。
- 登记在分支清单并标 `非本期`，需要时由 `05-design-repo-layout.md` 的分层规则决定是否单独开视图。
- **不得因为"反正画都画了"塞进当前视图**——这是"面面俱到"最主要的来源。

## 四、主干优先在设计流程中的落点

主干优先不是一句口号，它落在四个具体位置：

| 位置 | 落点 |
| --- | --- |
| `08-design-decision-tree.md` 节点 1-2 | US 与 F 层先只写主干用例与主干功能，可选项登记为分支 |
| `08-design-decision-tree.md` 节点 3（I 层） | 先产 `*Main` 步骤视图并 ⏸ 确认，再逐条展开分支视图 |
| `08-design-decision-tree.md` 节点 4（UI 层） | 先做主干交互反馈，错误/空/无权限状态归入分支 |
| `10-design-reasoning.md` 横向扩散 | 扩散出的分支不得就地改主干，走主干变更门禁 |
| `checklists/model-quality.md` | 交付前逐项核对 |

## 五、反模式

| 反模式 | 为什么错 |
| --- | --- |
| 一张图里同时画主干 + 3 个异常 + 2 个降级 + 导出 | 面面俱到实则混乱，评审时无人能定位问题 |
| 主干未确认就开始逐分支画图 | 分支越多主干越难被独立审视，最终全盘返工 |
| 分支视图重复画一遍主干全部步骤 | 图变宽三倍，读者要自己去比对差异 |
| 分支展开时"顺手"给主干加节点 | 主干失去共识基线，三个月后无人说得清主干是什么 |
| 把外围需求（导出 / 批量 / 兼容）塞进本期视图 | 图里 30% 是不本期内容，直接降低可读性 |
| 分支视图不带接缝锚点说明 | 读者无法知道该分支从主干哪里岔出 |
| 主干视图 `include *` 一次性全包含 | 等于把所有分支塞回主干，违反 T2 |
| 用"内容完整"为超限辩护 | 完整不等于可评审。评审要在一次阅读中抓住主干 |

## 六、交付时必须说明

七层或任意视图交付时追加：

1. **主干是什么**：一句话 + 主干路径（触发 → 结果）。
2. **分支清单**：每条分支的编号、条件、归属层、优先级、是否本期。
3. **视图分工**：哪些视图是主干视图、哪些是分支视图，各自回答什么问题。
4. **容量核对**：每张视图的元素 / 步骤数是否在上限内。
5. **冻结状态**：主干是否已冻结；本次是否发生过主干变更（若有，附门禁记录）。
6. **未展开的分支**：登记但未画的分支及原因（本期不做 / 待补充 / 非本期）。
