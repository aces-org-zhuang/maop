# SOP 06: Architecture Handoff

## 目标

把架构模型转成**可交接的实现输入**,让实现阶段不必重新分析架构。本 SOP 产出 `implementation-delivery` 能直接消费的规格,同时与 `technical-design` 已有的 Handoff 契约衔接,不重复造轮子。

## When Required

- 架构模型完成并通过 `likec4 validate` 后,进入实现准备阶段
- 实现方需要知道「有哪些组件、边界在哪、依赖怎么走、部署要求是什么」
- `technical-design` 需要架构事实作为其设计输入
- 架构变更后需要重新评估实现影响面

## 核心定位：架构规格是交接的子集,不是替代

架构模型**推不出**代码实现。它能回答「有什么、在哪里、怎么连」,不能回答「怎么做、对不对」。

| 架构规格能提供 | 仍需 technical-design 提供 |
| --- | --- |
| 组件清单与职责边界 | 接口签名、参数类型 |
| 依赖方向与约束 | 错误处理、业务规则 |
| 部署拓扑与运行时要求 | 数据结构、ORM 模型 |
| 关键流程时序 | 边界条件、验收细则 |

**因此本 SOP 的产出是 `Implementation Handoff Mini-Spec` 的架构视角子集**,由 `technical-design` 补齐接口与数据细节后形成完整交接包。本技能不产出可执行代码,也不声称「架构即开发」。

```text
architecture-design（本 SOP）
  └─ 架构规格：组件/边界/依赖/部署/流程
       ↓
technical-design
  └─ 补齐接口契约、数据结构、业务规则 → 完整 Technical Handoff Packet
       ↓
implementation-delivery
```

若需求较小、架构未变,可用本 SOP 的规格直接进入实现,不必强制走完整技术设计。

## 执行步骤

### 1. 从模型取事实,不要凭记忆写

优先经 MCP 查询,避免手抄出错:

```
search-element            定位元素与所在 project
read-project-summary      了解全局结构、可用 kind
subgraph-summary          取组件树与子元素
query-incomers-graph      取上游依赖
query-outgoers-graph      取下游影响面
read-deployment           取部署实例与节点
```

MCP 不可用时读取 `.c4` 源文件,并说明取自哪个文件。

### 2. 产出架构规格

按 `templates/architecture-handoff-spec.md` 输出,必含五部分:

| 部分 | 内容 | 设计链来源 |
| --- | --- | --- |
| 组件边界 | 每个组件的职责、归属环、禁止越界 | `model` 元素的 description |
| 依赖约束 | 谁调谁、方向、禁止反向依赖 | **F 侧的功能边界**（依赖方向的依据）+ `query-outgoers-graph` |
| 流程锚点 | 关键链路的时序视图 id | I 环的 `dynamic view` view id |
| 部署要求 | 运行时实例、环境、资源 | SRC 环 + `deployment` 模型 |
| 验收锚点 | 每个组件的可验证信号 | **NF 侧的可度量值**（验收依据）+ 组件职责 + 部署约束 |

**每一条都必须能追溯到模型元素或视图 id。** 写不出模型依据的内容标记为 `待补充`,不凭空补齐。

### 2.1 交接起点是 Feature，不是单环

交接规格的**范围单位是 Feature**,不是某个环的零散元素。规格开头必须写清:

```text
交接范围：Feature-001 结算下单
交付边界：客服在对话中可直接完成下单
Feature 类型：F 类（对外可见能力新增）
所属愿景：让交易更顺
```

**为什么**：单看 I 环或 SRC 环的组件,实现方无法判断这个组件服务于哪次交付、边界在哪。Feature 是最小的可交付单位,也是交接的最小完整范围。

**NF 类 Feature 的交接要点**：能力不变,本次交付的是质量提升。规格中须显式说明「F 侧无需新增功能单元」,否则实现方会以为有功能遗漏。

### 2.2 F / NF 必须出现在交接映射里

旧版交接映射只写了 I / UI / SRC 三环,**F 与 NF 缺失**。这是不对的:

| 设计链位置 | 交接到哪一部分 | 为什么 |
| --- | --- | --- |
| **F 侧** | 依赖约束 | 功能边界即依赖方向的依据。没有 F 边界,「谁调谁」无从判断 |
| **NF 侧** | 验收锚点 | 可度量值即验收依据。没有 NF 值,「怎样算完成」是空的 |
| I 环 | 组件边界 | 业务语义与步骤决定组件职责 |
| UI 环 | 交互与信息 | 前端据此实现界面 |
| SRC 环 | 部署要求 | 源码单元对应运行时实例 |

**NF 侧为空时必须显式说明**,不能沉默跳过——分不清是「确实无质量要求」还是「忘了评估」。

### 3. 落盘位置与发现机制

规格**放在设计仓,不放主仓 docs**。设计仓承载架构资产,主仓 docs 承载规则与索引,两者职责不混。

```text
<design-repo>/
  src/**/*.c4                 架构模型
  handoff/
    current.md               当前生效的架构交接规格
    history/<commit>.md      历史版本,按模型 commit 命名
```

**为什么放设计仓**:规格是架构模型的派生物,必须与被引用的模型版本同处一个 commit。放主仓会出现"规格说 A、模型是 B"的错配,而主仓无法独立验证它对应哪个模型版本。

**为什么主仓 docs 不放**:主仓 docs 放的是规则、索引和需与代码同 PR 的内容。规格会随模型演进频繁改版,放主仓会制造大量跨仓 PR。

**发现机制(下游技能必须遵循)**:

1. 规格路径固定为 `vendor/design/<design-repo-name>/handoff/current.md`,不靠约定之外的猜测。
2. 文件头必须写明模型 commit。下游读到 commit 与主仓 pinned 不一致时,规格视为过期,必须先更新指针。
3. 文件不存在表示架构交接尚未产出,下游按各自的默认路径工作,不报错、不阻塞。
4. 下游**只读不改**规格。需要修正架构时回到本技能重新产出,不在下游手改。

### 4. 标注置信度

关键架构结论置信度低于 90% 时,不得声明 ready,只能输出缺口与补证动作。置信度依据:

- 模型有明确 description 且无冲突 → 高
- 仅靠元素名推断 → 中,需用户确认
- 依赖外部系统且未验证 → 低,必须标注

### 5. 判断交接路径

| 条件 | 路径 |
| --- | --- |
| 架构未变,仅补实现细节 | 架构规格 + `implementation-delivery` |
| 架构有变更或新增组件 | 架构规格 → `technical-design` 补接口与数据 → 实现 |
| 架构本身尚未定版 | 先完成建模与评审,不产出交接规格 |
| 架构变更影响多个模块 | 先 `reasoning-map` 收敛影响面,再产出规格 |

### 6. 与项目规则同步

架构变更后,项目仓 `AGENTS.md` 的设计仓规则与 `docs/02-development/submodules-index.md` 的 pinned 值需同步。主仓 PR 需说明关联的设计仓提交。

## 与其他技能的边界

- **不替代 `technical-design`**。接口契约、数据结构、业务规则仍由它产出。
- **不生成代码**。本技能无代码生成能力,也不应假装具备。
- **不跳过建模**。模型未通过 `likec4 validate` 时不产出交接规格。
- **不改主仓代码**。架构变更落在设计仓,主仓只更新指针。

## 常见 RED 点

- 产出「架构即代码」的承诺:架构推不出业务规则,强行生成会产出看似完成实则空心的实现。
- **交接范围没写清是哪个 Feature**:实现方拿到一堆组件,不知道服务于哪次交付、边界在哪。
- **依赖约束里没有 F 侧功能边界**:只有「谁调谁」没有「为什么允许这么调」,依赖约束就只是现状描述。
- **验收锚点里没有 NF 侧可度量值**:验收标准变成主观描述,测试无据可依。
- **NF 侧为空时沉默跳过**:分不清是「确实无质量要求」还是「忘了评估」。
- **NF 类 Feature 未说明 F 侧「无需新增」**:实现方以为有功能遗漏,补出超范围代码。
- 规格里的组件职责与模型 description 不一致,实现方按规格做但模型是另一回事。
- 依赖方向写反:模型里 `a .depends b`,规格写成 `b 依赖 a`。
- 流程锚点给出不存在的 view id,实现方无法查阅。
- 置信度全部标 100%:没有说明依据的置信度等于没有置信度。
- 架构刚变更就交接,用的是旧模型的规格。

## 交付标准

交付时说明:

1. 架构模型位置与 `likec4 validate` **及 `build`** 结果(两者都要)
2. **交接范围**:Feature 编号与标题、交付边界一句话、Feature 类型(F 类 / NF 类)、所属愿景
3. 架构规格落盘位置、取事实的方式(MCP 或读文件)
4. **五部分各自对应的设计链来源**,含 F 侧与 NF 侧如何落到依赖约束与验收锚点
5. 置信度与未达 90% 的项
6. 交接路径判断结论
7. 哪些内容必须由 `technical-design` 补齐
8. F / NF 的双向边校验结果（每个 F 有 `US → F` 入边，每个 NF 有指向 US 的 `.trace` 边）
