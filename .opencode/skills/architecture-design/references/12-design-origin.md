# SOP 12 - 产品愿景与设计起点（Vision → Feature → US → …）

## 目的

`07-design-chain.md` 定义**每一环该产出什么**。本 SOP 定义**从哪里开始**——即设计链起点的判定、交付边界的确定，以及 `Feature` 与 `US` 之间的归属关系。

跳过这一步，设计就从「需求描述」起步，等于默认需求已经清楚。设计最大的价值恰恰在那个还没被问出来的问题：**这次到底要解决什么。**

---

## 一、设计链结构

```text
产品愿景        长期方向，作为坐标原点
 ↓
Feature        一次可交付增量，按切分维度分两条链

下钻路径（两条链完全相同）
      US → I → UI → SRC

切面标注（不是路径环节）
      Feature-<序号>-F    tag: capability   能力单元清单 = {F 单元}
      Feature-<序号>-NF   tag: quality      能力单元清单 = {NF 单元}

 ↓
构建部署    SRC 的运行投影，交付落地后才产出
```

**下钻路径只有一条。US 下钻到 I，中途不经过 F 或 NF。**

**F 与 NF 是能力单元清单**，与 US 并列，同为 Feature 的直接子元素。**Feature 才是 US 的超集。**

详见第三节。

---

## 二、为什么起点是 Feature 而不是更细的东西

### 起点必须可证伪

一条设计链的起点要能被业务方否决，否则整条链的严肃性无从建立。判据只有一个：

> **能否问出「不是这个」，并得到认真的否定回答？**

|候选起点 | 可证伪性 | 能否作起点 |
| --- | --- | --- |
| 产品愿景 | 弱。问「愿景对吗」，只会得到「对啊」 | **否**，仅作坐标原点 |
| Feature | 强。问「这次要交付的是这个吗」，业务方能说「不是，要的是那个」 | **是** |
| US | 中。但它已在 Feature 的边界之内，范围已定 | 否，已在链中 |
| 单个操作步骤 | 无意义。删掉它只是少一个实现细节 | 否，属 I 层 |

**变更起点只能是 Feature 或 Feature 以下。** 愿景只能被继承，不能被追溯——每个 Feature 声明服务于哪个愿景，反向不要求查。

### 为什么不从 US起步

从 US 起步等于**假设需求已清楚**。US 是别人给出的答案，从答案起步就只能验证它做得好不好，无法质疑它该不该做。

这会直接导致 US 颗粒度失控：

```text
起点没有交付边界
   ↓
US 只能从原始需求描述里切
   ↓
切的时候没有判据 → 按操作步骤切
   ↓
US 颗粒度过细，追溯链从US 就断了
```

**Feature 层提供了参照系**：每条 US 都要能回答「它服务于本次交付的哪一部分」。答不上来的 US 删掉也不影响交付——那是多余的。

## 三、F 与 NF 是能力单元清单，不是路径环节

`Feature` 按**切分维度**分为两类，两类**本体相同、维度不同**：

| | F 链 | NF 链 |
| --- | --- | --- |
| 切分维度 | 按业务能力 | 按质量属性 |
| tag | `capability` | `quality` |
| 能力单元清单 | F 单元（订单功能、支付功能） | NF 单元（性能、可审计性、可用性） |
| 回答 | 能做什么 | 做到什么程度 |
| 是否有 US | 有 | **有** |
| 是否有 I / UI / SRC | 有 | **有** |

### F 与 NF 不在下钻路径上

```text
下钻路径    US → I → UI → SRC          两条链相同
清单        {F 单元} 或 {NF 单元}      与 US 并列，非路径环节
```

**US 下钻到 I，中途不经过 F 或 NF。** 把它画成 `US → F → I` 会造成两个错误误解：

1. **暗示 F 属于 US**——箭头读作包含，但实际 F 与 US 是 `Feature ⊃ {US, 清单}` 里的并列子集
2. **暗示必须经过 F 才能到 I**——把旁挂的清单挤进了必经路径

**Feature 才是 US 的超集**，它同时容纳 US、能力单元清单、I / UI / SRC。

### 关键：两者同维度，不是「功能 vs 约束」

**F 与 NF 都是可交付的能力单元，不是一个是实体、另一个是属性。**

F 链的 US 与 NF 链的 US 结构完全相同——都有角色、场景、期望、可判定的验收。**NF 链的 US 不比 F 链的 US 缺任何东西。**

```text
F 链的 US   作为客服，我能直接为客户下单，以便当场完成交易。验收：2 秒内返回订单号。
NF 链的 US  作为客服，下单超 200ms 时系统提示异常，以便我能立刻知道要重试。验收：提示明确可操作。
```

第二条同样是完整的能力承诺，只是它交付的是**性能感知上的确定性**，而不是交易功能本身。

### 判定

```text
本次交付新增或改变了一项业务能力        → F 链
本次交付提升或保障了某项质量属性        → NF 链
两者都有                              → 拆成两条链，清单各自独立
```

**不要用占比判定。** 「功能占 80% 还是 30%」没有可观察锚点，写进文档会退化成贴标签仪式。

### 两条链各自完整闭环，NF 不挂在 F 的链上

```text
下钻路径    US → I → UI → SRC              两条链相同
F 链清单    Feature-001-F   { F 单元 }
NF 链清单   Feature-001-NF  { NF 单元 }
```

**同一条路径跑两遍，只是切分维度与清单不同。** NF 链里的一切都是它自己的：有自己的 US、自己的 I 逻辑、自己的 SRC。

**链内不出现对方元素。** 推 F 链到底不需要 NF，NF 链也不需要 F。

**清单项与 US 的对应边是清单语义，不是路径环节**：

```c4
us_place .trace f_order '要求'      // OK：订单功能是 US-001 要求的
us_peak .trace nf_latency '要求'    // OK：响应时延是 US-003 要求的
```

这两条边说明清单项的来源，**不意味着 US 要经过 F / NF 才能到 I**。

**禁止的边**（把切面挂进另一条链，或挂进路径）：

```c4
nf_latency .trace i_step '约束步骤耗时'// 错：NF 挂进路径环节
nf_auditability .trace i_state '约束状态迁移' // 错：同上
```

**为什么错**：这等于在推 F 的过程中「顺手检视一下 NF」。切面一旦进入路径，就会在每次推进时被反复提及，最终把 F 的视图撑爆——这正是本 SOP 要避免的混乱。

### 禁止跨链边（硬约束）

```c4
nf_latency .trace feat_checkout_f.i_step '约束步骤耗时'       // 错：NF 挂进 F 链
nf_auditability .trace feat_checkout_f.i_state '约束状态迁移' // 错：同上
nf_latency .trace feat_checkout_f.us_place '约束验收标准'     // 错：NF 指向 F 链的 US
```

**跨链边是硬错误。** 它等于在推 F 的过程中「顺手检视一下 NF」——切面一旦进入主链，就会在每次推进时被反复提及，最终把 F 的视图撑爆。

**正确做法**：NF 链拥有自己的 US 与 I 环。性能切面交付的是「超时能被感知并可操作」这项能力，它有自己的业务逻辑，不需要借用 F 链的。

### 文件物理隔离

两条链是**平级的独立 Feature**，各占一个文件：

```text
src/model/
  feature-001-f-checkout.c4     Feature-001-F 结算下单
  feature-001-nf-perf.c4        Feature-001-NF 支付性能
```

编号用 `Feature-<序号>-F` 与 `Feature-<序号>-NF` 成对，靠序号关联交付主题。

**为什么不用同一个 Feature 下的双侧**：文件嵌套本身就是一种「顺便检视」的暗示。只要 NF 住在 F 的目录里，AI 和人都会在推 F 时忍不住去看它。平级分文件是**物理隔离**，比口头约定可靠。

### 增量设计与全量设计

| 模式 | 做法 |
| --- | --- |
| **增量设计** | 一次只推一条链。做 F 增量就只推 F 链，做 NF 增量就只推 NF 链，**不因为「顺手」把另一条链拽进来**。链内推演完成后**跨链接力**起对方链的新推演 |
| **全量设计** | **每一环都要有全景视图**（F / NF / US / I / UI / SRC 六张），外加 **SRC 源码文件目录视图** |

**聚合只发生在全景层，不发生在链视图层。**

**SRC 环为何特殊**：它是唯一带真实磁盘资产的环（源码路径写在 `description` 里），因此必须有目录视图，否则实现方只拿到抽象单元，看不到实际文件布局。

详见 `07-design-chain.md` 第五节。

### Feature 何时省略

```text
该 Feature 下只有 1 条 US → 省略 Feature 层，直接用该 US
该 Feature 下有 2 条以上 US → 保留，因为它回答「这批为什么一起做」
```

判据与设计链的通用逻辑一致：**答不上问题的环节就该去掉。**

## 四、归属关系：每一环都不孤立

每一环的元素都必须能回答「我归属于哪个 Feature」。在LikeC4 中这靠**嵌套**表达，不靠文字说明。

```c4
model {
  feat_checkout = feature 'Feature-001 结算下单' {
    description '本次交付：客服在对话中可直接完成下单。'

    us_place = userStory 'US-001 提交订单' {
      description '作为客服，我能在对话中直接为客户下单。'
    }
    us_pay = userStory 'US-002 完成支付' {
      description '作为客服，我能在下单后立即发起支付。'
    }

    i_step = implStep 'I-001 业务步骤' {
      description '提交订单 → 校验库存 → 发起支付 → 确认。'
    }

    src_checkout = srcUnit 'SRC-001 结算入口' {
      description 'src/routes/checkout-routes.js'
    }

    i_step .trace src_checkout '落到实现'
  }
}

views {
  //视图作用域指向 Feature，容器自动带上
  view usLayer of feat_checkout {
    title 'US 层视图 · 归属于 Feature-001'
    include *
  }

  // 跨作用域引用嵌套元素须用 FQN
  dynamic view trunkSeq {
    variant sequence
    title '主干时序'
    include feat_checkout.us_place, feat_checkout.i_step
    feat_checkout.us_place -> feat_checkout.i_step '触发'
  }
}
```

> 实测记录（likec4 1.58.0）：上述写法 `✓ Valid` 且 `build` 输出 `✓ all views layouted`。

**收益**：任一层视图单独打开时，读者立刻知道它服务于哪个 Feature——这正是「每层都不孤立」的结构保证。详见 `02-multifile-and-fqn.md`。

## 五、产品愿景的地位

愿景是坐标原点，**不承载追溯门禁，不作变更起点**。

```text
愿景  →  方向校验（防止 Feature 漂离）
Feature  →  范围裁决（可被业务方证伪）
```

**为什么不让愿景承载门禁**：愿景不可证伪。若把它设为正式起点，「上升到愿景确认范围」这一步会变成走过场——向上确认不出任何东西。

**为什么不落成模型元素**：愿景是文本方向，不需要被 query。写成 `description` 里的说明即可，避免为不可校验的东西引入校验成本。

---

## 六、变更起点的上升路径

```text
起点在 SRC / UI / I / US
   → 上升到 Feature，确认「本次交付范围是否仍成立」
   → 若超出该 Feature 范围，走范围裁决
   → 仍超出现有 Feature 范围时，新建 Feature 而非扩展既有的
```

**上升的终点是 Feature，不是 US。** US 之上是 Feature，US 处停下意味着没确认范围。

详见 `10-design-reasoning.md`。

---

## 七、交付边界确认清单

进入设计链之前逐项确认：

- [ ] 交付边界已写成一句话，且业务方能说「不是」
- [ ] **切分维度已判定**：F 链（业务能力）/ NF 链（质量属性）/ 两者都要
- [ ] **F 与 NF 按同维度理解**，未被建模为「功能 vs 约束」
- [ ] 编号为 `Feature-<序号>-F` / `Feature-<序号>-NF`，序号配对
- [ ] **一次只推一条链**，未把另一条链拽进来
- [ ] **无跨链边**：NF 链不引用 F 链元素，反之亦然
- [ ] NF 链的 US 与 F 链 US 结构同构（有角色、场景、期望、可判定验收）
- [ ] 每条链下的 US 条数 ≥ 2（只有 1 条时已省略 Feature 层）
- [ ] 每条链声明服务于哪个产品愿景
- [ ] 愿景未被用作变更起点或追溯门禁
