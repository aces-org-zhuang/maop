# SOP 12 - 产品愿景与设计起点（Vision → Feature → US → …）

## 目的

`07-design-chain.md` 定义**每一环该产出什么**。本 SOP 定义**从哪里开始**——即设计链起点的判定、交付边界的确定，以及 `Feature` 与 `US` 之间的归属关系。

跳过这一步，设计就从「需求描述」起步，等于默认需求已经清楚。设计最大的价值恰恰在那个还没被问出来的问题：**这次到底要解决什么。**

---

## 一、设计链七环

```text
产品愿景        长期方向，作为坐标原点
 ↓
Feature层一次可交付增量，F 类 / NF 类二选一
 ↓
US          意图与验收标准
 ↓
I           业务目标、业务状态、业务步骤（不含源码）
 ↓
UI          交互设计、信息设计
 ↓
SRC类设计、组件设计、时序、数据流，须绑定真实路径
 ↓
构建部署    SRC 的运行投影，交付落地后才产出
```

**F（功能框架）与 NF（非功能框架）不再是独立环节**，它们是 `Feature` 层的内部分类，见第三节。

---

## 二、为什么起点是 Feature 而不是更细的东西

### 起点必须可证伪

一条设计链的起点要能被业务方否决，否则整条链的严肃性无从建立。判据只有一个：

> **能否问出「不是这个」，并得到认真的否定回答？**

|候选起点 | 可证伪性 | 能否作起点 |
| --- | --- | --- |
| 产品愿景 | 弱。问「愿景对吗」，只会得到「对啊」 | **否**，仅作坐标原点 |
| Feature | 强。问「这次要交付的是这个吗」，业务方能说「不是，要的是那个」 | **是** |
| US | 中。但它已在 Feature 的边界之内，范围已定 | 否，已在链中 |
| 单个操作步骤 | 无意义。删掉它只是少一个实现细节 | 否，属 I 层 |

**变更起点只能是 Feature 或 Feature 以下。** 愿景只能被继承，不能被追溯——每个 Feature 声明服务于哪个愿景，反向不要求查。

### 为什么不从 US起步

从 US 起步等于**假设需求已清楚**。US 是别人给出的答案，从答案起步就只能验证它做得好不好，无法质疑它该不该做。

这会直接导致 US 颗粒度失控：

```text
起点没有交付边界
   ↓
US 只能从原始需求描述里切
   ↓
切的时候没有判据 → 按操作步骤切
   ↓
US 颗粒度过细，追溯链从US 就断了
```

**Feature 层提供了参照系**：每条 US 都要能回答「它服务于本次交付的哪一部分」。答不上来的 US 删掉也不影响交付——那是多余的。

---

## 三、Feature 的两类

`Feature` 有且仅有两类，判据是**本次交付是否改变对外可见的能力**。

### 判定

| 类型 | 判定标准 | 描述 |
| --- | --- | --- |
| **F 类** | 对外可见能力**新增或改变** | 通常功能为主、质量为辅 |
| **NF 类** | 对外可见能力**不变**，某个质量属性是本次主要交付物 | 纯质量提升 |

**不要用占比判定。** 「功能占 80% 还是 30%」没有可观察锚点，写进文档会退化成贴标签仪式。

真实反例：一个支付接口逻辑极简（三次调用），但性能与一致性要求极高——功能占比 10%，若按占比会被误判为 NF 类。判据问的是「对外可见能力是否变化」，不是「功能代码占多少」。

### 两类都要建立 US 体系

**NF 类 Feature 不得跳过 US 层。** 这是硬要求。

理由：质量目标必须落到某个人的可感知收益上，否则无法验收。纯写「P95 ≤ 200ms」没人能验收——业务方能验收的是「不卡」。

对比两种写法：

```text
不合格  本次做到：优化支付性能
        可观察：P95 ≤ 200ms

合格    本次做到：月末结算高峰，客服不用再手工刷新状态
        可观察：20 并发下单 P95 ≤ 200ms，且客服侧无需刷新
```

**验收标准必须把指标值与用户体验绑在一起。**

### F 环在 NF 类中的处理

NF 类 Feature 的 F 环**不是缺失，而是「显式声明无需新增」**。

不显式写的话，追溯门禁无法区分「确实无需新增」与「忘了做」——前者是设计结论，后者是缺口。

### Feature 何时省略

```text
该 Feature 下只有 1 条 US → 省略 Feature 层，直接用该 US
该 Feature 下有 2 条以上 US → 保留，因为它回答「这批为什么一起做」
```

判据与设计链的通用逻辑一致：**答不上问题的环节就该去掉。**

## 四、归属关系：每一环都不孤立

每一环的元素都必须能回答「我归属于哪个 Feature」。在LikeC4 中这靠**嵌套**表达，不靠文字说明。

```c4
model {
  feat_checkout = feature 'Feature-001 结算下单' {
    description '本次交付：客服在对话中可直接完成下单。'

    us_place = userStory 'US-001 提交订单' {
      description '作为客服，我能在对话中直接为客户下单。'
    }
    us_pay = userStory 'US-002 完成支付' {
      description '作为客服，我能在下单后立即发起支付。'
    }

    i_step = implStep 'I-001 业务步骤' {
      description '提交订单 → 校验库存 → 发起支付 → 确认。'
    }

    src_checkout = srcUnit 'SRC-001 结算入口' {
      description 'src/routes/checkout-routes.js'
    }

    i_step .trace src_checkout '落到实现'
  }
}

views {
  //视图作用域指向 Feature，容器自动带上
  view usLayer of feat_checkout {
    title 'US 层视图 · 归属于 Feature-001'
    include *
  }

  // 跨作用域引用嵌套元素须用 FQN
  dynamic view trunkSeq {
    variant sequence
    title '主干时序'
    include feat_checkout.us_place, feat_checkout.i_step
    feat_checkout.us_place -> feat_checkout.i_step '触发'
  }
}
```

> 实测记录（likec4 1.58.0）：上述写法 `✓ Valid` 且 `build` 输出 `✓ all views layouted`。

**收益**：任一层视图单独打开时，读者立刻知道它服务于哪个 Feature——这正是「每层都不孤立」的结构保证。详见 `02-multifile-and-fqn.md`。

## 五、产品愿景的地位

愿景是坐标原点，**不承载追溯门禁，不作变更起点**。

```text
愿景  →  方向校验（防止 Feature 漂离）
Feature  →  范围裁决（可被业务方证伪）
```

**为什么不让愿景承载门禁**：愿景不可证伪。若把它设为正式起点，「上升到愿景确认范围」这一步会变成走过场——向上确认不出任何东西。

**为什么不落成模型元素**：愿景是文本方向，不需要被 query。写成 `description` 里的说明即可，避免为不可校验的东西引入校验成本。

---

## 六、变更起点的上升路径

```text
起点在 SRC / UI / I / US
   → 上升到 Feature，确认「本次交付范围是否仍成立」
   → 若超出该 Feature 范围，走范围裁决
   → 仍超出现有 Feature 范围时，新建 Feature 而非扩展既有的
```

**上升的终点是 Feature，不是 US。** US 之上是 Feature，US 处停下意味着没确认范围。

详见 `10-design-reasoning.md`。

---

## 七、交付边界确认清单

进入设计链之前逐项确认：

- [ ] 交付边界已写成一句话，且业务方能说「不是」
- [ ] Feature 类型已判定（F 类 / NF 类），判定依据是对外可见能力是否变化
- [ ] NF 类 Feature 已建立 US 体系，验收标准含用户体验
- [ ] Feature 下的 US 条数 ≥ 2（只有 1 条时已省略 Feature 层）
- [ ] 每个 Feature 声明服务于哪个产品愿景
- [ ] 愿景未被用作变更起点或追溯门禁
