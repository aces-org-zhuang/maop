# 七层设计链（US → F/NF → I → UI → SRC → 构建部署）

## 目的

架构不是画一张系统图就结束。一个需求从提出到落地要穿过七层，每层都有**不同的读者、不同的语言、不同的验收标准**。混在一起会导致业务方看不懂、工程师没细节、评审无法定位问题。

本 SOP 定义这七层的边界、命名、产出物与追溯要求。

落盘骨架见 `templates/seven-layer-chain.md`，其中所有 `.c4` 代码块均经 likec4 1.58.0 实测通过（`✓ Valid (7 files)` → `build` 无布局错误 → `All 7 file(s) are formatted`）。

```text
US  用户故事        起点：谁、要什么、验收标准
 ↓
F   功能框架        系统提供哪些能力
 NF  非功能框架      质量属性约束：性能、安全、可审计、可维护
 ↓
I   实现层          业务目标、业务状态、业务步骤（不含源码）
 ↓
UI  界面层          交互设计（系统如何反馈）、信息设计（展示什么）
 ↓
SRC 源码层          类设计、组件设计、时序图、数据流图
 ↓
构建与部署           交付落地之后才做
```

---

## 一、各层职责与边界

### US 层 · 用户故事

**产出物**：用户故事清单，每条含 `US-<编号> <标题>`、用户角色、期望、验收标准。

**回答的问题**：谁在什么场景下要完成什么，做成什么样算完成。

**不属于本层**：技术方案、界面细节、类设计。

### F 层 · 功能框架

**产出物**：`F-<编号> <功能名>`，描述系统对外提供的能力单元。

**回答的问题**：系统能做什么。

**不属于本层**：具体实现、业务步骤、界面元素。

### NF 层 · 非功能框架

**产出物**：`NF-<编号> <质量属性名>`，如性能、可用性、安全性、可审计性、可维护性、兼容性。

**回答的问题**：系统必须做到什么程度。

**必须可度量**。「系统要快」不合格；「下单 P95 ≤ 500ms」合格。无法度量的 NF 项应标记为 `待补充`，不凭想象编造。

### I 层 · 实现层（业务设计）

**产出物**：`I-<编号> <类型> <名称>`，三类：

| 编号段 | 内容 | 判据 |
| --- | --- | --- |
| 业务目标 | 该功能要达成的业务结果 | 描述收益，不描述手段 |
| 业务状态 | 业务对象的生命周期状态机 | 状态名 + 允许迁移 |
| 业务步骤 | 达成目标的操作序列 | 步骤 + 参与角色 |

**这一层完全不涉及源码**。判断标准：**换一个人、换一种技术栈来实现，这层设计依然成立**。一旦出现类名、函数名、表名，就越界了。

**为什么单独设 I 层**：业务方评审时看的就是这层。如果业务目标、状态、步骤混在技术方案里，业务方无法评审——这是设计与需求脱节的根因。

### UI 层 · 界面层

**产出物**：`UI-<编号> <类型> <名称>`，两类，缺一不可：

| 类型 | 内容 | 必须回答 |
| --- | --- | --- |
| 交互设计 | 系统对用户操作的响应 | 每个操作触发什么、反馈什么、失败怎么回退、可否撤销 |
| 信息设计 | 系统需要展示的信息 | 字段、列表、可见区域、筛选区域、扩展功能（通知、导出、批量操作） |

**交互设计不等于界面布局**。按钮长什么样、颜色如何是视觉设计；交互设计关注的是**行为与反馈**。

**信息设计的常见遗漏**：空状态、加载状态、错误状态、无权限状态。这四种必须在设计里出现，否则实现时会临时发明，导致不一致。

### SRC 层 · 源码层

**产出物**：`SRC-<编号> <单元名>` + 真实文件路径。

**回答的问题**：代码怎么组织。

**必须绑定真实路径**。`SRC-002 订单服务 → src/services/order-service.js`，而不是「订单服务模块」。没有路径约束的 SRC 层会与实际代码脱节。

**本层可包含**：类设计、组件设计、时序图、数据流图、依赖方向。

**边界**：I 层说「状态如何迁移」，SRC 层说「哪个类的哪个方法执行迁移」。前者不含源码，后者必须含。

### 构建与部署

**不属于设计六层**，是交付之后的环节。

只有当设计落地为代码后才产出：CI 流程、镜像、环境拓扑、发布策略、回滚方案。**在设计阶段不产出构建部署图**——它依赖最终实现，提前画必然返工。

例外：部署形态会影响架构决策（如是否需要跨网络隔离），此时只记录**约束**，不画完整部署图。

## 二、命名规范（强制）

| 层 | 格式 | 示例 |
| --- | --- | --- |
| US | `US-<三位编号> <标题>` | `US-001 结算下单` |
| F | `F-<三位编号> <功能名>` | `F-001 订单功能` |
| NF | `NF-<三位编号> <质量属性>` | `NF-001 可审计性` |
| I | `I-<三位编号> <类型> <名称>` | `I-002 业务状态 订单状态机` |
| UI | `UI-<三位编号> <类型> <名称>` | `UI-002 信息设计 订单列表信息` |
| SRC | `SRC-<三位编号> <单元名>` | `SRC-002 订单服务` |

编号**全局唯一且不复用**。删除元素后编号不回收，避免历史引用失效。

**语言**：编号与显示名分隔。编号前缀是英文（跨工具稳定），显示名用中文。依据 `01-likec4-basics.md` 的语言契约。

## 三、追溯要求（硬门禁）

### 每个 US 必须有完整链路

```text
US → 至少一个 F 或 NF → I → UI → SRC
```

**任一层缺失即为不完整设计**，必须在交付时明确报告缺失哪一层，不能静默跳过。

理由：层间追溯是这套体系的全部价值。如果 US 直接连到 SRC，就退化成「画了个系统图」，业务方无法参与，评审无法定位断点。

### 追溯关系要写明语义

关系标签必须说明**为什么连接**，不能只写「关联」。

```c4
us_checkout -> f_order '要求'
nf_auditability -> i_state '约束状态迁移'
ui_interaction -> src_checkout '触发'
```

### 反向检查

每个 SRC 单元应能回答：**它服务于哪个 I 层步骤或 UI 元素**。答不上的 SRC 单元属于超范围实现，应报告为待确认项。

## 四、LikeC4 映射（1.58.0 实测）

### element kind 定义

```c4
specification {
  element userStory { style { shape document } }
  element function   { style { shape rectangle } }
  element nonFunction { style { shape mobile } }
  element implStep   { style { shape rectangle } }
  element uiSurface  { style { shape browser } }
  element srcUnit    { style { shape component } }
  element system
}
```

**shape 合法值实测**：`rectangle` `component` `storage` `cylinder` `browser` `mobile` `person` `queue` `bucket` `document`。**没有 `hexagon`**，非功能框架用 `mobile` 或 `cylinder` 区分。

### 三个实测约束

| 约束 | 说明 |
| --- | --- |
| **不支持通配 include** | `include f_*` 会报 `Expecting token of type '}' but found '*'`。分层视图必须逐个列出元素 |
| **sequence 必须有消息** | 只有 `include` 没有消息时，布局报 `actors array must not be empty`，且 `likec4 validate` 仍通过——**只 validate 发现不了** |
| **sequence 只连叶子元素** | 同既有约束，`variant sequence` 下不可连有子元素的容器 |

第二条尤其要注意：`validate` 通过但 `build` 失败。只跑 validate 会漏掉。

### 必备视图

必备的跨层视图如下，各层专属视图见下一节：

| 视图 | 覆盖层 | 用途 |
| --- | --- | --- |
| 链路总览 | US → SRC 全链 | 架构评审 |
| 业务设计视角 | US/F/NF/I/UI，**不含 SRC** | 业务方确认 |
| 源码实现视角 | I/UI/SRC | I 层如何落到代码 |
| 功能与非功能框架 | US + F + NF | 产品与架构 |
| 设计时序 | I/UI/SRC，`variant sequence` | 工程师 |

## 五、层与视图类型的对应关系

**视图类型由层的性质决定，不由「是否跨文件」决定。** 每层的读者不同，视图的形态也不同。

| 层 | 主视图类型 | 可用视图类型 | 主要读者 | 关键要求 |
| --- | --- | --- | --- | --- |
| US | `element view`（index 入口） | element | 全体 | 一个 US 一个可导航入口 |
| F / NF | `element view` | element | 产品与架构 | NF 项与 F 项同图可见，便于对照 |
| I | `dynamic view`（步骤序列） | dynamic + Mermaid 状态机 | 业务方 | **不含 SRC 元素** |
| UI | `element view`（交互面） | element + 表格 | 设计与前端 | 交互与信息设计都要出现 |
| SRC | `element view` + `variant sequence` | element + dynamic + 数据流 | 工程师 | 嵌套引用需 FQN |
| 构建部署 | `deployment view` | deployment | 运维 | 交付后才产出 |

### 为什么这样分配

- **US / F / NF 是静态结构**，用 `element view` 表达「谁包含谁、谁要求谁」。
- **I 层的核心是步骤与状态**。步骤序列用 `dynamic view`（diagram 变体）；**状态机必须走 Mermaid `stateDiagram-v2`**，LikeC4 1.58.0 完全无法表达状态机。
- **UI 层是静态面 + 动态反馈的组合**：交互面用 element view 表达「哪个界面触发哪个行为」，信息设计（字段、列表、筛选区、通知）用表格更清晰，硬塞进图会失焦。
- **SRC 层是唯一需要多种视图的层**：组件结构用 element view，调用时序用 `variant sequence`，数据流向用 Mermaid flowchart 或 element view 的依赖关系。
- **构建部署用 `deployment view`**，且只在交付落地后产出。

### 跨层视图

除各层自己的视图外，必须有跨层视图承载追溯链：

| 视图 | 覆盖层 | 用途 |
| --- | --- | --- |
| 链路总览 | US → SRC 全链 | 架构评审，一图看全 |
| 业务设计视角 | US / F / NF / I / UI | **排除 SRC**，供业务方确认 |
| 源码实现视角 | I / UI / SRC | I 层如何落到代码 |
| 设计时序 | I / UI / SRC | `variant sequence`，须含显式消息 |

**业务设计视角排除 SRC 是硬要求。** 业务方评审时看到源码元素就失去焦点，这是本层的意义所在。

### 视图命名的层归属

视图名建议带层前缀，便于导航与检索：

```text
us-<编号>          用户故事视图
frame-<名称>       F / NF 框架视图
impl-<名称>        I 层步骤视图
ui-<名称>          UI 层视图
src-<名称>         SRC 层视图
chain-<名称>       跨层链路视图
dep-<环境>         部署视图
```

视图名**全局唯一**，不同文件间也不能重名。**不要使用视图文件夹分组**——1.58.0 不支持 `views 'Label'`，按用途拆文件、用文件名表达层归属。

### 视图与多文件的关系

视图类型和文件组织是两件事：

- **视图类型**由层性质决定（上表）
- **文件组织**按层拆分，详见 `02-multifile-and-fqn.md`
- **FQN 规则只属于 SRC 层**：只有 SRC 层大量嵌套，跨文件引用才必须 FQN。上五层扁平，short name 即可

## 六、按层路由到不同工具

七层不是所有内容都该用 LikeC4。能力边界必须诚实：

| 层 | 轨道 | 说明 |
| --- | --- | --- |
| US / F / NF | **一（LikeC4）** | 结构化关系，AI 可查询 |
| I 业务状态 | **二（Mermaid）** | 状态机 LikeC4 不支持；`flowchart` 或 `stateDiagram-v2` |
| I 业务步骤 | **一（LikeC4 dynamic view）** | 步骤序列可表达 |
| UI 交互 | **一（dynamic view）+ 二** | 反馈流程用 LikeC4；复杂分支用 Mermaid |
| UI 信息 | **二（Mermaid / 表格）** | 字段与列表结构用表格更清晰 |
| SRC 类设计 | **三（PlantUML）** | LikeC4 不支持类图与继承 |
| SRC 组件与依赖 | **一（LikeC4）** | 组件划分与依赖方向 |
| SRC 时序与数据流 | **一（dynamic view）+ 二** | 简单用 LikeC4，条件分支用 Mermaid |
| 构建部署 | **一（deployment view）** | 交付后产出 |

**注意 I 层业务状态的路由**：LikeC4 1.58.0 不支持状态机（`opt`/`loop`/`alt`/`try` 均不可用）。业务状态机是 I 层的核心产出，**必须走 Mermaid `stateDiagram-v2`**。这不违反"架构真源在 LikeC4"——状态机是业务设计而非架构拓扑，本就不属于 LikeC4 的表达范围。

## 七、交付标准

七层设计交付时说明：

1. 覆盖的 US 清单，以及每条 US 的链路是否完整（缺哪层）
2. 各层产出物位置：LikeC4 模型文件 / Mermaid 文件 / 表格位置
3. **各层使用的视图类型**，以及是否与本 SOP 第五节的对应表一致
4. LikeC4 版本与 `likec4 validate` **及 `build`** 结果（两者都要，只 validate 会漏掉布局错误）
5. 哪些层走了轨道二/三及原因
6. SRC 层的文件路径是否已核对真实代码
7. SRC 层是否使用了 FQN 引用嵌套元素（上五层不应被迫使用）
8. NF 项中无法度量的条目
9. 构建部署图是否产出（应说明为何未产出或已产出）
