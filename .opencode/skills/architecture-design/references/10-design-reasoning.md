# SOP 10 - 设计双向推演（影响面闭环）

## 目的

`08-design-decision-tree.md` 定义了**怎么问用户**。本 SOP 定义**怎么推演影响面**——确保任何设计变更的关联影响都分析到位。

单向推演会漏东西：

- 从 Feature 往下推，只覆盖"这个需求明确要求的内容"
- 从 SRC 往上推，只覆盖"这行代码影响的东西"

两者都不完整。**真正的风险在中间环**：源码改了但界面没改、业务语义变了但验收标准没变、功能框架变了但 NF 没补。

## 核心原则

**只有 Feature 是闭环的开端。只要起点不是 Feature，就必须先上升到 Feature 确认交付范围，再重新下钻。**

这不是"源码起点才需要上升"——**I 环、UI 环、US 环、F/NF 环作为起点同样需要上升**。区别只是要跨几环，不是要不要上升。

| 起点 | 是否上升 | 说明 |
| --- | --- | --- |
| **Feature** | 否 | 闭环的开端，直接逐环下钻 |
| **F / NF** | 是 → 到 Feature | 问：本次交付的功能边界或质量约束是否要变 |
| **US** | 是 → 到 Feature | 问：这条 US 是否还在本次交付范围内 |
| **I** | 是 → 到 Feature | 问：业务目标、状态、步骤是否要变 |
| **UI** | 是 → 到 Feature | 问：这次界面改动对应什么业务意图 |
| **SRC** | 是 → 到 Feature | 问：落点与依赖变化是否超出本次交付 |

**为什么任何非 Feature 起点都必须上升**：

不从交付边界出发，就会漏掉至少一件事：

- 界面改了但业务意图没变——那这个界面改动凭什么存在？
- 业务语义变了但验收标准没变——验收标准失真，测试会按旧标准放过错误
- 功能框架变了但 NF 没补——新增依赖常带来质量属性缺口
- 实现做了需求之外的事——无人要求的功能静静进了系统

**上升到 Feature 的真正目的**：确认这次改动**没有超出本次交付范围**。超出时这是需要用户裁决的时刻，不是继续推演的时刻。

**产品愿景不是上升终点**。愿景可证伪性弱（问「愿景对吗」只会得到「对啊」），把它设为门禁会让上升这一步变成走过场。上升止于 Feature。

## 红绿循环（推演的核心机制）

推演不是一次画完的图，而是**红绿交替的收敛过程**。每一轮做三件事：

```text
第 1 步  给当前视野内的每个节点打标
         🟢 已覆盖 / 有意边界化（附理由）
         🔴 缺口 / 未验证假设 / 待扩散

第 2 步  选一个最宽泛的 🔴，判断走向
         藏多职责、跨边界、有状态转换  -> 下钻
         影响主链路之外的相邻关注点      -> 横向扩散

第 3 步  取当前可获得的最高保真证据，把 🔴 转 🟢 或边界化
         真实代码 / MCP 模型查询 / 问用户 / 契约检查
         不得用推测代替证据

未闭环 -> 回到第 1 步，进入下一轮
```

**每轮必须输出当前推演图**（`Round N Map`），让用户看到判断如何演进，而不是只在最后给结论。

### 为什么必须是循环而不是一次画完

一次画完的问题是：画图时没有新信息，图上的红点只是**看起来像缺口的东西**，不是**验证过的缺口**。循环的价值在于每轮都有新证据进来，红点的消失有据可查。

### 红绿语义

| 标记 | 含义 |
| --- | --- |
| `🟢` | 已验证覆盖 / 已有实现 / 有意边界化（必须附理由） |
| `🔴` | 设计缺口 / 未验证假设 / 证据不足 / 待扩散 / 需求实现脱节 |

**证据不足就是 `🔴`**，不引入"可能没问题"的中间态。

## 模式参考

沿用 `reasoning-map` 的模式，不发明新体系：

- **红绿循环**：上述三步循环，每轮输出地图
- **渐进地图**：每轮输出 `Round N Map`，不在最后一次性给结论
- **RED/GREEN 标记**：`🔴` 未闭环 / 设计缺口，`🟢` 已覆盖 / 有意边界化
- **图优先**：关键结论画在图里，不用 Markdown 表格承载
- **闭环停止条件**：每个 `🔴` 都有依据、边界或验证动作才停
- **MECE 检查**：每层分解要互斥且穷尽

## 路径 A · 自上而下（起点 Feature）

```text
Round 1  [Feature-001 结算下单 {交付边界一句话}]
              |
              v  下钻
Round 2  [US-001 提交订单] [US-002 完成支付]
              |                |
              v                v  横向扩展
Round 3  [F-001 订单功能] [NF-001 可审计性] [I-002 业务步骤]
              |                                |
              v                                v
Round 4  [UI-001 交互设计]  [SRC-002 订单服务]  <-- 闭环
```

**每一环下钻时问三个问题**：

1. 这一环是否需要新增内容？（不是"有没有"，是"需不需要"）
2. 这一环是否需要修改既有内容？
3. 同环内还有谁受影响？（横向扩展）

**横向扩展的触发条件**（满足任一即扩散）：

| 条件 | 例子 |
| --- | --- |
| 新增了关系或依赖 | SRC 加了调用 → 查反向依赖者 |
| 新增了对外可见行为 | 加了状态 → 查所有读该状态的界面 |
| 触及跨切约束 | 引入外部依赖 → 全部 NF 项复查 |
| 触及共享状态或数据 | 改了存储结构 → 查所有读写方 |

**横向扩展的边界**：扩散出的分支即使无关也要标 `🟢` 并说明理由，不留悬空。

### 扩散不得破坏主干（硬约束）

横向扩散出来的内容**不得就地写进主干模型或主干视图**。它只能：

1. 登记为分支（`BR-nn`：条件 / 归属层 / 优先级），进入分支清单；或
2. 标 `🟢 边界化` 并附理由。

**若扩散结论表明主干本身有问题**（例如主干漏了一个必经步骤），这不是「顺手补一下」的时刻——走 `11-trunk-first-design.md` 的主干变更门禁：

```text
⏸ 主干变更请求
发现阶段：Round N 横向扩散
变更内容：主干 <...> 之间缺少 <...>
原因：<哪条 BR 分支暴露的>
影响：<受影响环>
请裁决：1. 主干回退重新确认  2. 把该分支边界化
```

**为什么**：扩散的本质是找边界，它天然会不断侵蚀主干。每一次「顺手补」都让主干失去共识基线，最终没人说得清主干到底是什么。规则见 `11-trunk-first-design.md` 第三节。

## 路径 B · 先上升再下钻（起点为任意非 Feature 环）

**适用起点**：US / F / NF / I / UI / SRC。**共同动作**：先上升到 Feature 确认交付范围，再逐环下钻。

```text
Round 1  [起点：I-002 业务状态 {改动：新增退款分支}]
              |
              v  上升（关键：不能跳过）
Round 2  [Feature-001 结算下单 {⏸ 范围裁决} {🔴 该退款是否在交付边界内}]
              |
              v  范围确认后重新下钻
Round 3  [US-003 退款申请 {是否仍属本次交付？}]  [F-002 支付功能 {框架是否变？}]
              |
              v
Round 4  [UI-001 交互设计 {界面是否需同步？}]  [SRC-004 退款服务 {落点确认}]
```

### 上升时每环必问

上升路径是**从起点往上到 Feature**，经过的环取决于起点在哪。**不要跳过途经的任何一环**——每环都有本环特有的遗漏风险。

**升到 I 环**（起点在 I 或更低时必经）：

- 业务语义是否变了？还是实现变了但语义没变？
- 状态机是否需要新增状态或迁移？
- 业务步骤是否新增分支？（注意：`opt`/`alt` 不可用，拆视图）
- **判定**：换个人、换技术栈，这环设计是否仍成立？若不成立，说明越界写成了实现细节。

**升到 UI 环**（起点在 UI 或更低时必经）：

- 界面行为是否需变？用户看到的还是旧行为吗？
- 信息设计的字段、列表、筛选区是否受影响？
- 四种状态（空 / 加载 / 错误 / 无权限）是否有变化？
- **反向也要问**：这次界面改动对应哪个业务步骤？找不到对应就是无源之水。

**升到 F / NF 侧**（起点在 F/NF 或更低时必经）：

- 功能边界是否变？是否新增了功能单元？
- 新增的依赖是否带来新的质量要求？
- 现有 NF 项是否被破坏？（引入第三方调用常破坏可审计性与可用性）
- Feature 类型是否需要重判？（原为 F 类，现是否变成 NF 类？反之亦然）

**升到 US 环**（起点在 US 时必经）：

- 这条 US 是否仍在本次交付边界内？
- 业务目标是否仍然一致？
- 验收标准是否需要修改？
- 它挂的那个 Feature 是否还成立？

**升到 Feature 环（⏸ 所有非 Feature 起点都必须停下）**：

- 这次改动是否仍在本次交付边界内？
- 可观察结果是否仍然可达？
- Feature 类型是否需要改变？

### 各起点在上升时要额外确认

| 起点 | 上升路上额外要确认的 |
| --- | --- |
| US | 这条 US 是否只是实现便利的产物，而非真实用户诉求？ |
| F / NF | 新增的功能单元或质量约束是否对应真实用户诉求？还是技术便利驱动的？ |
| I | 业务语义变更是否已获业务方认可？还是实现者自行解释的？ |
| UI | 界面改动是否掩盖了 I 环的语义缺失？（常见：界面先动，业务语义没定） |
| SRC | 落点与依赖变化是否引入了新的质量要求？ |

### 范围裁决

**若答案是"超出了本次交付边界"**——立即停下，向用户说明：

```text
⏸ 范围裁决
变更起点：<哪一环>
变更内容：<具体改了什么>
超出范围：该能力未在 Feature-001 的交付边界内体现
需要确认：
  1. 扩展 Feature-001 的交付边界，还是
  2. 新建独立 Feature 承接该能力
用户确认后再继续下钻。
```

**这不是可以自行决定的事。** 任何环的实现替业务扩大了交付范围，都必须由用户裁决——不只是 SRC 环。

### 下钻时的注意点

上升确认范围后重新下钻，与路径 A 同样要做横向扩展。**但要额外检查**：

- 上升过程中发现的问题，下钻时是否被真正处理？（如范围扩大后 I 层状态机是否补齐）
- 起点层的改动是否在更高层产生了连锁影响？（如 SRC 改动导致 I 层状态需要新增）

## 双向交叉：同一变更从两端进入

**最危险的情况是需求和实现同时推进**——需求方没说清，开发方先做了。

此时**两个方向都要走**，并且要显式交叉验证：

```text
自上而下发现：US-001 缺少"部分退款"场景
自下而上发现：SRC-004 已实现部分退款

交叉结论：需求与实现脱节
处理：
  1. 把发现写入 US-001 或新建 US
  2. 补 I 层状态与步骤
  3. 补 UI 层交互
  4. 重新验证 SRC-004 是否满足补齐后的验收标准
```

**发现需求与实现脱节时，这本身就是一个 `🔴` 红点**，必须在推演图中标出，不能跳过。

## 推演图格式

**每轮都要输出一张图。** 图是推演的载体，不是最后的总结附件。

```text
Round N Map: [阶段名] [起点：<哪一环>]

主干链（冻结后不得改）
[🟢 已覆盖 {依据}]
   -> [🔴 待处理 {当前证据或假设}]
        -> [🔴 待下钻 {下一轮要拆什么}]
             -> [🔴 连带影响 {同层还有谁}]

从 [🔴 某节点] 横向扩散
   ├─ [🟢 已排除 {理由}]
   ├─ [🔴 未闭环 {需要验证什么}]
   └─ [🟢 边界化 {如何确认无关}]

扩散出的分支（只登记，不并入主干）
   └─ [BR-nn 条件 / 归属层 / 优先级]

范围裁决（仅非 US 起点需要）
   └─ [⏸ 超出本次交付边界 {交用户裁决}]

主干变更（仅当扩散暴露主干缺陷）
   └─ [⏸ 主干变更请求 {交用户裁决}]
```

### 图的三条硬约束

| 约束 | 原因 |
| --- | --- |
| **每轮一张，不合并** | 让用户看到判断如何演进，而不是只看到结论 |
| **每个 `🔴` 有内联原因或验证动作** | 没原因的 `🔴` 等于没有 `🔴`，只是抱怨 |
| **关键结论在图内，不用表格** | 表格承载推演结论会让图退化为配图 |

**不要输出**：推演过程表、退出检查表、评分表、Mutation Log。这些是内部自检，不是交付内容。

**终端不显示 emoji 时**，整份推演改用 ASCII 备用标记，不要混用：

| emoji | ASCII 备用 | 含义 |
| --- | --- | --- |
| `🔴` | `[RED]` | 未闭环 / 设计缺口 / 未验证假设 |
| `🟢` | `[GREEN]` | 已覆盖 / 有意边界化 |

## 闭环停止条件

红绿循环**必须同时满足**以下条件才可停止：

1. 每个 `🔴` 都有以下结果之一：已补齐设计 / 已边界化影响面 / 有具体验证动作 / 明确列为待补证
2. **起点若非 Feature，已上升到 Feature 确认交付范围**（或已明确记录需要用户裁决）
3. 每个受影响环的链路完整，无缺失环
4. 需求与实现的一致性已交叉验证
5. 扩展出的横向分支均已标记（`🟢` 边界化或 `🔴` 有动作），且**未并入主干模型**
6. 每轮都输出了图，且图中红点的消失有据可查
7. **主干已冻结**：若本轮修改了主干，已走主干变更门禁并留下裁决记录

**默认最大深度**：一个变更涉及的层数（通常 3-5 层）。不因追求深度而无限扩散。

**不停止的情况**：

- 还有 `🔴` 停留在"需下钻但没下"
- 还有 `🔴` 没有原因也没有验证动作
- **起点不是 Feature 却未上升到 Feature 就停了**
- 需求与实现的一致性未验证
- 只出了一张最终图，没有分轮推演
- **主干未确认就展开了分支**
- **扩散出的分支被就地并入了主干模型或主干视图**

**红点转绿必须有证据变化。** 如果某轮没有取到任何新证据，只是重画了一遍图，那不是推进——是空转。空转说明推演卡住了，此时应改变策略（换更高保真的证据来源，或把问题明确交用户），而不是继续画图。

## 取事实的方式

推演结论应基于当前可获得的最高保真证据，**不靠猜**：

| 层 | 取事实方式 |
| --- | --- |
| SRC | 真实代码目录、入口文件、既有实现；必要时经 MCP 查依赖者 |
| UI | 现有界面代码或原型；无则标 `🔴 需用户确认` |
| I | 已有状态机与步骤；注意不能从源码反推业务语义，**必须问用户** |
| F / NF | 已有模型与既有 NF 项；新增依赖的影响需外部资料佐证 |
| US | **只能问用户**，不推测 |

**关键**：I 环与 US 环的业务语义**不能从源码反推**。改了代码不等于业务目标变了，也不等于没变——这必须问。这是最容易出错的地方。

## 与决策树的关系

| 阶段 | 用什么 |
| --- | --- |
| 节点 -1 交付边界与 Feature 类型确认后 | 先按本 SOP 推演，确定影响哪些环 |
| 推演确定环范围后 | 按 `08-design-decision-tree.md` 的节点 1-6 与用户交互 |
| 推演发现范围超出交付边界 | 停下，走本 SOP 的范围裁决 |
| 推演闭环后 | 按 `06-architecture-handoff.md` 产出交接规格 |

**推演在前，交互在后。** 没有推演就逐环问用户，会问出没有影响面依据的问题。

交付边界与 Feature 类型的判定规则见 `12-design-origin.md`。
