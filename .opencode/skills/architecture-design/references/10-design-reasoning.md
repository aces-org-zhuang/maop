# SOP 10 - 设计双向推演（影响面闭环）

## 目的

`08-design-decision-tree.md` 定义了**怎么问用户**。本 SOP 定义**怎么推演影响面**——确保任何设计变更的关联影响都分析到位。

单向推演会漏东西：

- 从 US 往下推，只覆盖"这个需求明确要求的内容"
- 从 SRC 往上推，只覆盖"这行代码影响的东西"

两者都不完整。**真正的风险在中间层**：源码改了但界面没改、业务语义变了但验收标准没变、功能框架变了但 NF 没补。

## 核心原则

**推演方向由起点决定，但终点都是闭环。**

| 起点 | 方向 | 终点 |
| --- | --- | --- |
| US / F / NF（自上而下） | 逐层下钻 + 每层横向扩展 | 落到 SRC 层闭环 |
| SRC / UI（自下而上） | 先上升到 US 确认范围，再逐层下钻 | 回到 US 确认业务目标未变 |

**为什么源码起点的路径必须上升**：

只改源码会漏掉三件事：

1. 界面是否需同步改——否则用户看到旧行为
2. 业务语义是否变——否则状态机与验收标准失真
3. 功能框架是否仍成立——否则 NF 出现缺口（比如新增了外部依赖却没补可审计性）

**上升到 US 的真正目的**：确认这次底层改动**没有超出原始需求范围**。如果超出了，这是需要用户裁决的时刻，不是继续推演的时刻。

## 模式参考

沿用 `reasoning-map` 的模式，不发明新体系：

- **渐进地图**：每轮输出 `Round N Map`，不在最后一次性给结论
- **RED/GREEN 标记**：`🔴` 未闭环 / 设计缺口，`🟢` 已覆盖 / 有意边界化
- **图优先**：关键结论画在图里，不用 Markdown 表格承载
- **闭环停止条件**：每个 `🔴` 都有依据、边界或验证动作才停
- **MECE 检查**：每层分解要互斥且穷尽

## 路径 A · 自上而下（起点 US）

```text
Round 1  [US-001 结算下单]
              |
              v  下钻
Round 2  [F-001 订单功能] [F-002 支付功能] [NF-001 可审计性]
              |                    |
              v                    v  横向扩展
Round 3  [I-002 业务状态]  [I-003 业务步骤]  [UI-001 交互设计]
              |                                        |
              v                                        v
Round 4  [SRC-002 订单服务]  [SRC-003 支付客户端]  <-- 闭环
```

**每层下钻时问三个问题**：

1. 这一层是否需要新增内容？（不是"有没有"，是"需不需要"）
2. 这一层是否需要修改既有内容？
3. 同层内还有谁受影响？（横向扩展）

**横向扩展的触发条件**（满足任一即扩散）：

| 条件 | 例子 |
| --- | --- |
| 新增了关系或依赖 | SRC 加了调用 → 查反向依赖者 |
| 新增了对外可见行为 | 加了状态 → 查所有读该状态的界面 |
| 触及跨切约束 | 引入外部依赖 → 全部 NF 项复查 |
| 触及共享状态或数据 | 改了存储结构 → 查所有读写方 |

**横向扩展的边界**：扩散出的分支即使无关也要标 `🟢` 并说明理由，不留悬空。

## 路径 B · 自下而上（起点 SRC）

```text
Round 1  [SRC-002 订单服务 {改动：新增支付方式分支}]
              |
              v  上升（关键：不能跳过）
Round 2  [UI-001 交互设计 {界面是否需同步？} {🔴 缺口}]
              |                          |
              v                          v
Round 3  [I-002 业务状态 {状态是否变？}]  [F-002 支付功能 {框架是否变？}]
              |                          |
              +------------+-------------+
                           v
Round 4  [NF-001 可审计性 {是否破坏？}]  [US-001 结算下单 {⏸ 范围裁决}]
```

### 上升时每层必问

**升到 UI 层**：

- 界面行为是否需变？用户看到的还是旧行为吗？
- 信息设计的字段、列表、筛选区是否受影响？
- 四种状态（空 / 加载 / 错误 / 无权限）是否有变化？

**升到 I 层**：

- 业务语义是否变了？还是实现变了但语义没变？
- 状态机是否需要新增状态或迁移？
- 业务步骤是否新增分支？（注意：`opt`/`alt` 不可用，拆视图）
- **判定**：换个人、换技术栈，这层设计是否仍成立？若不成立，说明越界写成了实现细节。

**升到 F / NF 层**：

- 功能边界是否变？是否新增了功能单元？
- 新增的依赖是否带来新的质量要求？
- 现有 NF 项是否被破坏？（引入第三方调用常破坏可审计性与可用性）

**升到 US 层（⏸ 必须停下）**：

- 这次改动是否仍在原始需求的范围内？
- 业务目标是否仍然一致？
- 验收标准是否需要修改？

**若答案是"超出了原始需求"**——立即停下，向用户说明：

```text
⏸ 范围裁决
底层改动：SRC-002 新增支付方式分支
超出范围：该能力未在 US-001 的验收标准中体现
需要确认：
  1. 扩展 US-001 的验收标准，还是
  2. 新建独立用户故事承接该能力
用户确认后再继续下钻。
```

**这不是可以自行决定的事。** 底层实现替业务扩大了需求范围，必须由用户裁决。

---

## 双向交叉：同一变更从两端进入

**最危险的情况是需求和实现同时推进**——需求方没说清，开发方先做了。

此时**两个方向都要走**，并且要显式交叉验证：

```text
自上而下发现：US-001 缺少"部分退款"场景
自下而上发现：SRC-004 已实现部分退款

交叉结论：需求与实现脱节
处理：
  1. 把发现写入 US-001 或新建 US
  2. 补 I 层状态与步骤
  3. 补 UI 层交互
  4. 重新验证 SRC-004 是否满足补齐后的验收标准
```

**发现需求与实现脱节时，这本身就是一个 `🔴` 红点**，必须在推演图中标出，不能跳过。

---

## 推演图格式

```text
Round N Map: [阶段名]
[🟢 已覆盖内容 {依据}]
   -> [🔴 待处理内容 {当前证据或假设}]
        -> [🔴 待下钻 {下一轮拆什么}]

从 [🔴 某节点] 横向扩散
   ├─ [🟢 已排除 {理由}]
   ├─ [🔴 未闭环 {需要验证什么}]
   └─ [🟢 边界化 {如何确认无关}]
```

**约束**（沿用 reasoning-map）：

- 只用 `🔴` / `🟢`，不引入黄橙等中间状态
- 每个 `🔴` 必须有内联原因或验证动作
- 不用表格承载推演结论
- 不输出推演过程表、退出检查表、评分表
- 宽度控制在终端可读范围

**终端不显示 emoji 时**，整份推演改用 ASCII 备用标记，不要混用：

| emoji | ASCII 备用 | 含义 |
| --- | --- | --- |
| `🔴` | `[RED]` | 未闭环 / 设计缺口 / 未验证假设 |
| `🟢` | `[GREEN]` | 已覆盖 / 有意边界化 |

---

## 闭环停止条件

**必须同时满足**才可停止推演：

1. 每个 `🔴` 都有以下结果之一：已补齐设计 / 已边界化影响面 / 有具体验证动作 / 明确列为待补证
2. 路径 B 已回落 US 层确认范围（或已明确记录需要用户裁决）
3. 每个受影响层的链路完整，无缺失层
4. 需求与实现的一致性已交叉验证
5. 扩展出的横向分支均已标记（`🟢` 边界化或 `🔴` 有动作）

**默认最大深度**：一个变更涉及的层数（通常 3-5 层）。不因追求深度而无限扩散。

**不停止的情况**：

- 还有 `🔴` 停留在"需下钻但没下"
- 还有 `🔴` 没有原因也没有验证动作
- 路径 B 未上升到 US 就停了
- 需求与实现的一致性未验证

---

## 取事实的方式

推演结论应基于当前可获得的最高保真证据，**不靠猜**：

| 层 | 取事实方式 |
| --- | --- |
| SRC | 真实代码目录、入口文件、既有实现；必要时经 MCP 查依赖者 |
| UI | 现有界面代码或原型；无则标 `🔴 需用户确认` |
| I | 已有状态机与步骤；注意不能从源码反推业务语义，**必须问用户** |
| F / NF | 已有模型与既有 NF 项；新增依赖的影响需外部资料佐证 |
| US | **只能问用户**，不推测 |

**关键**：I 层与 US 层的业务语义**不能从源码反推**。改了代码不等于业务目标变了，也不等于没变——这必须问。这是最容易出错的地方。

---

## 与决策树的关系

| 阶段 | 用什么 |
| --- | --- |
| 节点 0 规模判定后 | 先按本 SOP 推演，确定影响哪些层 |
| 推演确定层范围后 | 按 `08-design-decision-tree.md` 的节点 1-6 与用户交互 |
| 推演发现范围超出需求 | 停下，走本 SOP 的范围裁决 |
| 推演闭环后 | 按 `06-architecture-handoff.md` 产出交接规格 |

**推演在前，交互在后。** 没有推演就逐层问用户，会问出没有影响面依据的问题。
