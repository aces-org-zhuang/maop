# ipd-uml

## 适用范围

**IPD 领域**：优先使用本 skill 的 11 种图表类型和经典案例

**非 IPD 领域**：参照 ASCII 官方语法自行生成图表
- 故事线、思维导图、价值观对比等非技术场景
- 使用 graph、flowchart、mindmap 等 ASCII 语法
- 同样支持转换为高清图片

## 支持的图表类型（11种）

1. E-R 图（实体关系图）- 数据库设计
2. 组件图 - 软件架构
3. 时序图 - 交互流程
4. 流程图 - 业务流程
5. DFD 图 - 数据流
6. 状态图 - 状态机
7. 用例图 - 需求分析
8. FMEA 图 - 故障分析
9. 威胁模型图 - 安全分析
10. 决策树 - 决策分析
11. 甘特图 - 项目排期

## 图表选择决策树

```
内容分析
├─ 涉及实体和关系？ → E-R 图
├─ 涉及模块/组件依赖？ → 组件图
├─ 涉及时间顺序的交互？ → 时序图
├─ 涉及条件分支和流程？ → 流程图
├─ 涉及数据处理和传递？ → DFD 图
├─ 涉及状态转换？ → 状态图
├─ 涉及用户场景？ → 用例图
├─ 涉及故障/失效分析？ → FMEA 图
├─ 涉及安全/威胁分析？ → 威胁模型图
├─ 涉及决策/条件判断？ → 决策树
└─ 涉及项目排期/时间线？ → 甘特图
```


## 注意事项
- 一个场景可能需要多种图表组合
- 优先选择最能表达核心信息的图表类型
- ASCII 语法必须正确，避免渲染错误
- 图表要简洁清晰，避免过度复杂
- **合理性约束**：每次输出 3-8 个图表，避免信息过载
- 根据内容复杂度选择图表数量：简单场景 3-4 个，复杂场景 6-8 个
- **使用 subgraph 分组**：当节点超过 8 个时，必须使用 subgraph 按逻辑分组，避免图表混乱
- **数据字典**：使用 Markdown Table 展示，不要用图表（E-R 图用于关系建模，数据字典用表格）
- **关系标签**：在图表中明确标注实体/组件之间的关系类型
- **状态图技巧**：使用 note right of 在状态外部标注多属性状态
- **flowchart 关系边**：可以用 -.<关系标签>.-> 表示关系，如 -.include.->

## temp 目录规范

**目的**：隔离临时文件，避免污染工作环境

**目录结构**：
```
temp/
└── ASCII/
    ├── pictures/     # 生成的图片
    └── *.mmd         # 临时 ASCII 文件
```

**使用规则**：
- 所有临时文件必须放在 `temp/` 目录
- 图片输出到 `temp/ASCII/pictures/`
- 发送后立即删除，不保留
- temp 目录可随时清理

## 关系标签对照表

| 关系类型 | 符号/表示 | 含义 | 适用场景 | ASCII 示例 |
|---------|----------|------|---------|-------------|
| **包含** (Contains) | -.include.-> | A 包含 B，B 是 A 的一部分 | 用例图 | PlaceOrder -.include.-> CheckStock |
| **扩展** (Extends) | -.extend.-> | B 扩展 A 的功能 | 用例图 | Pay -.extend.-> UseCoupon |
| **泛化** (Generalization) | --|> | B 继承/泛化自 A | 类图、组件图 | Dog --|> Animal |
| **聚合** (Aggregation) | --o | A 聚合 B，B 可独立存在 | E-R 图、类图 | Department --o Employee |
| **组合** (Composition) | --* | A 组合 B，B 不能独立存在 | E-R 图、类图 | Car --* Engine |
| **关联** (Association) | -- 或 --> | A 与 B 有关联关系 | E-R 图、类图 | User -- Order |
| **依赖** (Dependency) | ..> | A 依赖 B，B 变化影响 A | 组件图、类图 | Service ..> Database |

### 关系强度对比

依赖 < 关联 < 聚合 < 组合（从弱到强）

## subgraph 分组最佳实践

### 原则
- 节点数 ≤ 8：可以不分组
- 节点数 > 8：必须使用 subgraph 分组
- 每个 subgraph 内节点数控制在 3-6 个
- 按逻辑层次分组（如前端/后端、输入/处理/输出、不同模块等）

### 分组策略
1. **按层次分组**：前端/中间件/后端/数据库
2. **按模块分组**：用户模块/订单模块/支付模块
3. **按流程分组**：输入/处理/输出
4. **按职责分组**：展示层/业务层/数据层

## 过度设计案例（禁止）

### 反例 1：简单 CRUD 功能过度可视化
错误做法：为一个简单的用户注册功能生成 10+ 个图
禁止原因：信息过载，简单功能不需要复杂可视化
正确做法：3 个图足够（时序图 + E-R图 + 流程图）

### 反例 2：为每个细节都画图
错误做法：为配置文件读取、日志输出等琐碎细节都生成独立图表
禁止原因：过度细化，淹没核心信息
正确做法：只为核心流程和关键决策点画图

### 反例 3：重复表达相同信息
错误做法：用多种图表表达同一个流程
禁止原因：信息冗余
正确做法：选择最合适的一种图表类型

### 反例 4：为了画图而画图
错误做法：内容简单却强行生成复杂图表
禁止原因：图表与内容不匹配
正确做法：内容简单时 1-2 个图或不画图

### 反例 5：所有场景都用全套图表
错误做法：无论什么场景都固定输出 11 种图表
禁止原因：忽略场景差异
正确做法：根据场景选择 3-8 个最相关的图表

## 使用方法

1. **分析内容特征**：识别内容类型（流程、架构、数据、状态、交互等）

3. **生成 ASCII 代码**：输出标准 ASCII 语法
4. **说明选择理由**：简要解释为什么选择这种图表类型
