## 工单目标
**目标**: 基于POC验证结果，验证系统是否满足验收标准

## Input（输入）
- **输入来源**: 上游工单（POC工单）
- **输入内容**: POC验证结果、可行性报告、改进建议
- **触发条件**: POC工单完成，验证通过

## 执行步骤

### Stage 1: 制定验收标准
[ ] Task: 制定验收标准
    操作(必选)：
        Step1: 使用验收标准技能完成验收标准制定
        Step2: 使用验收维度技能完成验收维度定义

### Stage 2: 设计验收方案
[ ] Task: 设计验收方案
    操作(必选)：
        Step1: 使用验收计划技能完成验收计划制定
        Step2: 使用验收用例技能完成验收用例设计

### Stage 3: 执行验收测试
[ ] Task: 执行验收测试
    操作(必选)：
        Step1: 使用功能验收技能完成功能验收测试
        Step2: 使用性能验收技能完成性能验收测试
        Step3: 使用安全验收技能完成安全验收测试
        Step4: 使用兼容性验收技能完成兼容性验收测试

### Stage 4: 创建下游工单
[ ] Task: 验证当前工单是否符合[交付物](##交付物)要求和[目录结构](##目录结构)
    操作(必选)：
        Step1: 验证交付物
        Step2: 验证目录结构

[ ] Task: 创建下游工单
    操作(必选)：
        Step1: 如果验收不通过，使用ticket-management技能创建下游工单（开发工单）

## Output（输出）
- **输出内容**: 验收报告、测试结果、质量评估、改进建议
- **下游工单**: 无
- **触发条件**: 验收完成，质量达标

## 异常场景和处理方式

| 错误代码 | 异常描述 | 处理动作 | 负责人 |
|----------|----------|----------|--------|
| ERROR:001 | 验收标准缺失 | 检查上游POC工单输出，重新制定验收标准 | 测试人员 |
| ERROR:002 | 测试环境不可用 | 检查环境配置，重启测试服务 | 运维人员 |
| ERROR:003 | 验收用例执行失败 | 分析失败原因，修复用例或提交缺陷 | 测试人员 |
| ERROR:004 | 性能指标不达标 | 记录性能数据，提交优化建议到开发工单 | 测试人员 |
| ERROR:005 | 安全漏洞发现 | 记录漏洞详情，创建安全缺陷工单 | 安全工程师 |

## 决策场景

| 触发条件 | 决策动作 | 预期结果 | 回退方案 |
|----------|----------|----------|----------|
| WHEN: 多个验收标准冲突 | THEN: **权衡优先级**：以生产环境要求为准，安全标准优先于性能标准 | 验收标准统一明确 | 采用最严格标准执行验收 |
| WHEN: 测试环境资源不足 | THEN: **权衡资源**：降级非核心功能测试，优先保障核心功能验证 | 核心功能验收完成 | 分批执行测试，延长验收周期 |
| WHEN: 验收结果存在争议 | THEN: **权衡证据**：以自动化测试结果为准，人工复核边界场景 | 验收结论客观公正 | 组织多方评审，达成共识后执行 |

## 观测模块

| 检查点 | 观测方法 | 预期状态 | 异常处理 |
|--------|----------|----------|----------|
| OBS_POINT: 验收环境状态 | OBS_METHOD: curl -f http://localhost:8080/health | HTTP 200 | 检查服务日志，重启服务 |
| OBS_POINT: 测试用例执行率 | OBS_METHOD: 检查测试报告中的执行统计 | 执行率 >= 95% | 补充缺失用例，重新执行 |
| OBS_POINT: 缺陷密度 | OBS_METHOD: 统计缺陷数量/代码行数 | 缺陷密度 < 阈值 | 提交开发工单进行修复 |
| OBS_POINT: 性能指标 | OBS_METHOD: 检查性能测试报告的响应时间和吞吐量 | 满足验收标准 | 记录性能瓶颈，提交优化建议 |

## 交付物

| 交付物 | 格式 | 说明 |
|--------|------|------|
| 验收报告 | Markdown | 包含验收结果、测试数据、质量评估 |
| 测试用例 | Markdown | 功能、性能、安全、兼容性测试用例 |
| 缺陷清单 | Markdown | 验收过程中发现的缺陷列表 |
| 质量评估 | Markdown | 系统质量综合评估报告 |

## 目录结构
```markdown
.aces/tickets/acceptance/{{execute_name}}/
├── input/                    # 输入文件目录
│   ├── meta.md                # 上游工单的元信息,包括工单目录和项目信息等等
│   └── features.md            # 特性明细 包括页面组件、WebApi验收等或特定函数FuncAPI验收等等
├── output/                  # 输出文件目录
│   ├── meta.md                # 验收项目的元信息,包括开发源码目录信息等等
│   ├── interactive_input.md   # 交互验收:页面可供交互的入口
│   ├── test_start.md                  # 启动验收:验收各组件启动命令
│   ├── test_end_to_end_trace_log.md   # e2e验收: 验收端到端效果的全链路日志展示
│   ├── test_exposed_api.md        # 暴露面接口验收
│   ├── snapshot/                  # 验收证据
│   │    ├── test-xx.md          # 功能1的EARS语法验收 展示各场景响应
│   │    ├── test-xx.md          # 功能2的EARS语法验收 展示各场景响应
│   │    └── .../      
│   └── report.md                # 验收报告
├── temp/                    # 临时文件目录
│   ├── cache/               # 缓存文件
│   ├── drafts/              # 中间草稿
│   └── logs/                # 处理日志
└── trace.md                 # 执行跟踪文件
```
